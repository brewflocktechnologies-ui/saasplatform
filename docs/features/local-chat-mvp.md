# Local chat MVP (specs/mvpsetup.spec.md)

> **Superseded by `docs/features/conversation-platform.md` (Plan 06).** The `chat` module and `/api/v1/demo/*` described below were removed; the V2 tables remain until a later migration drops them.

> **LOCAL POC — NOT REAL AUTHENTICATION.** Two hardcoded identities: visitor `userone` (Lit widget) and agent
> `agentbob` (Next.js dashboard). The caller names itself with `actorId`. This spec is **not** approval to deploy
> this identity model to UAT or production.

## Try it (two browsers)

```powershell
pnpm stack:up     # = docker compose -f docker-compose.yml -f docker-compose.apps.yml up --build -d --wait
```

| Browser | URL | Identity |
|---|---|---|
| A (e.g. Chrome) | http://localhost:5173/demo | visitor `userone` |
| B (e.g. Edge / other profile) | http://localhost:3000/agent | agent `agentbob` |

Both show a connection badge (`Connecting` → `Live`; `Reconnecting` / `Offline` on trouble). Send from A — it
appears in B without a refresh; reply from B — it appears in A. Reload either page: history comes back from
PostgreSQL. Host hot-reload mode works the same (`pnpm dev:backend`, `pnpm dev:dashboard`, `pnpm dev:widget`).

## Message flow

```text
widget/dashboard ──POST /api/v1/demo/conversations/{id}/messages──► Spring Boot (chat module)
   1 resolve demo actor (server derives VISITOR/AGENT)   2 check membership   3 trim + length check (≤4000)
   4 INSERT message + touch conversation in one transaction → COMMIT
   5 publish message.created → Centrifugo HTTP API (/api/publish, X-API-Key)   [realtime module]
        ├─► chat:conversation:<id>  → widget + dashboard (subscription JWT per actor + channel)
        └─► chat:inbox              → dashboard refetches the inbox from the API
   response 201 {message, realtimeDelivery: PUBLISHED | FAILED}
```

- **PostgreSQL is the source of truth.** A DB failure throws before any publication (unit-tested). If publishing
  fails after commit, the message stays saved and the response says `realtimeDelivery: FAILED`; the UI shows a
  "saved, live delivery failed" notice instead of a generic error (no blind resend).
- Delivery is **at-most-once** (publish-after-commit, no transactional outbox). Clients reload history from the API
  on every (re)subscribe and deduplicate by message id — verified by stopping Centrifugo, sending, and restarting it.
- Browsers never publish: the `chat` namespace has client publish/subscribe disabled; every subscription needs a
  backend-issued subscription JWT bound to `sub` + exact `channel` (5-minute TTL, separate HMAC secret).

## API (contract: `libs/contracts/openapi/platform-api.yaml`)

| Operation | Notes |
|---|---|
| `POST /api/v1/demo/conversations` | get-or-create the single OPEN conversation of userone (201 created / 200 reused); race-safe via partial unique index |
| `GET /api/v1/demo/conversations?actorId=agentbob` | inbox, most recent activity first; userone → 403, missing/unknown actor → 400 |
| `GET /api/v1/demo/conversations/{id}/messages?actorId=` | history ascending (`created_at, id`); 400 bad UUID/actor, 403 non-participant, 404 unknown |
| `POST /api/v1/demo/conversations/{id}/messages` | body `{actorId, text}`; 400 blank/too long/bad actor, 403, 404, 503 DB down |
| `GET /api/v1/demo/realtime/connection-token?actorId=` | `{token, expiresAt}` |
| `GET /api/v1/demo/realtime/subscription-token?actorId=&channel=` | agentbob: `chat:inbox` + assigned conversations; userone: own conversation only; 400 malformed, 403 cross-actor, 404 unknown |

Errors are RFC 9457 `application/problem+json` with no stack traces, SQL or secrets.

## Real-time events (contract: `libs/contracts/asyncapi/chat-realtime.yaml`)

| Channel | Events | Who may subscribe |
|---|---|---|
| `chat:conversation:<uuid>` | `message.created` | userone (own), agentbob (assigned) |
| `chat:inbox` | `conversation.created`, `message.created` (refresh signal) | agentbob |

Payload schemas: `libs/contracts/json-schema/chat/*.schema.json` (validated by `pnpm contracts:validate`, by
`chat-client` unit tests and against **live** Centrifugo publications in `tests/contract`).

## Data model (`database/flywayMigration/sql/V2__create_chat_tables.sql`)

- `chat_conversations(id uuid pk default uuidv7(), visitor_id, assigned_agent_id, status OPEN|CLOSED, created_at, updated_at, last_message_at)`
  + partial unique index `ux_chat_conversations_open_visitor (visitor_id) WHERE status='OPEN'`.
- `chat_messages(id uuid pk default uuidv7(), conversation_id fk, sender_id, sender_role VISITOR|AGENT, body
  CHECK (btrim non-empty AND ≤ 4000 chars), created_at)` + index `(conversation_id, created_at, id)`.
- IDs and timestamps are generated by the database, never accepted from the browser. Demo identities are enforced
  by the API (not the schema) so real identities can replace them. The runtime role `platform_app` has DML only.

Inspect rows without printing secrets:

```powershell
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select id, visitor_id, status, last_message_at from platform.chat_conversations" -c "select created_at, sender_id, sender_role, left(body, 60) from platform.chat_messages order by created_at desc limit 20"'
```

## Observability

- Metrics: `http_server_requests_seconds_*{uri=~"/api/v1/demo.*"}`, `chat_messages_persisted_total{role}`,
  `chat_realtime_publications_total{outcome}`; Grafana dashboard *Chat Platform - Local Overview* has chat panels.
- Logs (Loki): `{service_name="modulithplatformservice"} |~ "Message persisted|Centrifugo publish"` — ids only,
  never message bodies, tokens or keys.
- Correlation recipe: every response has `X-Trace-Id` → Tempo trace by id → Loki
  `{service_name="modulithplatformservice"} | trace_id="<id>"` → Prometheus metrics for the same `uri`.
- Centrifugo: `docker compose logs -f centrifugo`.

## Known limitations / before UAT or production

1. Replace `DemoActor` and the `actorId` parameter with real authentication (OIDC/session); authorize every API call
   and token request from the authenticated principal; tenant-scope channels.
2. Add a transactional outbox (or CDC) for reliable event delivery; current behaviour is at-most-once.
3. One open conversation, two identities, no tenancy, no assignment, closure, typing, receipts or attachments.
4. Centrifugo: single node, memory engine, no TLS, tokens HS256 with local secrets; production needs Redis/NATS
   engine, TLS/WSS, key rotation (`hmac_previous_secret_key`) and rate limits.
5. CORS/origins are hardcoded to localhost; API has no rate limiting or abuse protection.
