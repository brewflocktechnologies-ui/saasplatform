**Rulings used (Plan 01 ledger rulings).**
- `sequence` is gap-free: `last_sequence + 1` computed under the conversation row lock; tombstones keep their sequence; it numbers messages only.
- `conversation.created` and `conversation.updated` events carry the conversation `version`; `typing` carries neither. A `conversation.*` event whose `version` exceeds the known one by more than 1, or any conversation event while the client is not caught up, triggers a refetch of the conversation view.
- Centrifugo recovery has failed only when `wasRecovering=true && recovered=false` on the subscribed context; a bare `recovered=false` on a first subscribe is not a failure.
- The client always reconciles with `?after=<lastContiguous>` on every `subscribed`, including after a successful recovery; the delta fetch pages at most 5 times (limit 200), then the client takes the full-reload path (newest page, older pages on demand).

**External documentation consulted.** One source, read by the plan controller and relied on here only for the recovery-failure signal: Centrifugo history and recovery, <https://centrifugal.dev/docs/server/history_and_recovery>, accessed 27 Oct 2026. Everything else is local code or documentation inside the checkouts. The Zulip event-system page named in the spec was read as the local copy `docs/subsystems/events-system.md`, not from the web.

**Corrections applied to the notes (reviews found these after the notes were committed).** The matrix uses the corrected facts.

The automatic PENDING to OPEN on a human reply is a no-op in MIT code (`app/models/message.rb:423-433`, the guard `captain_pending_conversation?` is hard-coded false at `:431-432`); the working version is Enterprise-only (`enterprise/app/models/enterprise/message.rb:50-80` [EE-LICENCE]). The Enterprise production-use restriction is at `enterprise/LICENSE:6-12` [EE-LICENCE] (the note's section 0 says 1-2). Flood control runs on every validation including updates (`app/models/message.rb:67`).
- Rocket.Chat: the trash collection has a 30-day TTL (`packages/models/src/models/Trash.ts:18`), so hard deletes are visible to delta sync for 30 days only. Typing (note row 47) is ADAPT, not ADOPT. A duplicate client `_id` on the REST path probably errors (inference, row 3).

## 2. Where the notes and the decisions disagree (for Task 7)

The matrix follows the overview decisions and the ledger rulings. These are the places where an evidence note says something else, or where the decisions are silent.

1. **What carries `sequence`.** Chatwoot rows 9, 10 and 41, Rocket.Chat rows 40 and 43 and Zulip SI-1, SI-5, SI-12 propose a per-conversation `sequence` on every event, or system events inside the message sequence. The ledger ruling is narrower: `sequence` numbers messages only, conversation events carry `version`, typing carries neither. System and state events are therefore not messages and take no `sequence`. Task 7 should reword SI-1, SI-5 and SI-12 to "message events".
2. **Recovery-failure signal.** zulip.md SI-4 (b) and its test, and classification rows 3 and 7, say recovery "reported as failed (`recovered=false`)". The ledger ruling is `wasRecovering=true && recovered=false`. The matrix and Task 7 use the ruling.
3. **Tenant in the channel name.** zulip.md SI-11 says the channel name contains the tenant id, and Chatwoot row 31 and Rocket.Chat row 45 recommend tenant-scoped channels. D12 names `chat:conversation:<uuid>` without a tenant segment (only `chat:inbox:<tenantId>:<inboxUuid>` has one). D14 provides the isolation instead: the subscription token is refused for a conversation outside the caller's tenant. Whether to add the tenant to the conversation channel name would change D12 and is a controller decision, not mine.
4. **Typing label.** Chatwoot row 33 and Zulip row 25 say ADOPT, Rocket.Chat row 47 says ADAPT after correction. Row 16 above uses ADAPT.
5. **Idempotency key scope.** Chatwoot row 11 says "unique per conversation", Rocket.Chat row 4 "(tenant, conversation, sender)". D5 is `(conversation_id, sender_type, sender_id, client_message_id)`; equivalent in effect because the conversation id is a globally unique uuid and implies the tenant. No change needed; Task 7 should state it.
6. **Points the decisions D1 to D20 do not settle** (marked "open for T7" in the matrix): the per-tenant human conversation number; what `PENDING` means (Chatwoot row 3 is marked "confirm in T7"); the closed set of sender types; database-level tenant guards (composite foreign keys, row-level security); a single-snapshot read for history pages (zulip.md SI-13) against D3's READ COMMITTED; clamping the read cursor to the head (zulip.md SI-9); advancing the sender's own cursor on send; the payload shape of `data` (small delta); a guarded `UPDATE ... WHERE` per transition; a wider audit trail.
7. **Archive in Chatwoot.** The note's classification row 26 (REJECT) is replaced by n/a (not found), as instructed. The archive design is therefore built from our own requirement (D10) with Zulip's channel archive as the only close precedent.
8. **Refinements, not conflicts.** The cap of 5 delta pages (ledger) refines D12's "always reconcile". The gap-free rule (ledger) makes D4's wording ("`last_sequence` incremented under the lock") exact.
