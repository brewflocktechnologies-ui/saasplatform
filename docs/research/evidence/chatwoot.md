## 1. Conversation identity and lifecycle

- [code] The `conversations` table has an integer serial primary key, `account_id NOT NULL`, `display_id NOT NULL`, a `uuid` defaulting to `gen_random_uuid()`, and `status` integer default 0 NOT NULL (`db/schema.rb:990-1003`, `db/schema.rb:993`, `db/schema.rb:998`).
- [code] `display_id` is a per-account human number assigned by the database: an `accounts` after-insert trigger creates a Postgres sequence named `conv_dpid_seq_<account id>`, and a `conversations` before-insert trigger calls `nextval` on it (`db/schema.rb:1820-1832`; same logic restated in the model at `app/models/conversation.rb:437-440`; original migration `db/migrate/20230426130150_init_schema.rb:852`, `db/migrate/20230426130150_init_schema.rb:858`). A unique index covers `(account_id, display_id)` (`db/schema.rb:1019`). After create-commit the model re-reads `display_id` and `uuid` from the database (`app/models/conversation.rb:377-384`).
- [code] `uuid` has a unique index (`db/schema.rb:1036`) and a model uniqueness validation (`app/models/conversation.rb:83`). It is used for the public CSAT survey link (`app/models/conversation.rb:263-265`). Authenticated API routes address a conversation by `display_id` within `Current.account`, not by uuid or primary key (`app/controllers/api/v1/accounts/conversations_controller.rb:189-192`, `app/controllers/api/v1/accounts/conversations/base_controller.rb:6-9`).
- [code] The status enum has four values, including a snooze state: `enum status: { open: 0, resolved: 1, pending: 2, snoozed: 3 }` (`app/models/conversation.rb:86`). `pending` is the "bot owns it" state: a conversation in an inbox with an active bot is created pending and gets the bot as assignee (`app/models/conversation.rb:316-334`), a bot handoff only works from `pending` (`app/models/conversation.rb:184-193`), and a contact that is blocked produces a conversation created already `resolved` (`app/models/conversation.rb:316-317`). The public API schema lists only `open, resolved, pending` for the resource but also `snoozed` for the toggle endpoint (`swagger/definitions/resource/conversation.yml:52` [doc], `swagger/paths/application/conversation/toggle_status.yml:5-11` [doc]).
- [code] Transitions are not modelled. `toggle_status` flips open to resolved and sends pending or snoozed back to open, and carries the comment that a state machine is still to be implemented (`app/models/conversation.rb:172-177`). The API can assign any enum value directly (`app/controllers/api/v1/accounts/conversations_controller.rb:83-94`, `app/controllers/api/v1/accounts/conversations_controller.rb:176-179`). [inference] There is no transition table: any status can be written from any status, subject only to enum validity.
- [code] Status side effects live in model callbacks: `snoozed_until` is cleared unless snoozed (`app/models/conversation.rb:290-292`), `status_changed_at` is stamped on change (`app/models/conversation.rb:294-296`), and `waiting_since` is cleared via `update_column` when resolved (`app/models/conversation.rb:281-288`). After-commit callbacks emit the status events and write an activity message (`app/models/conversation.rb:142-146`, `app/models/conversation.rb:273-279`, `app/models/conversation.rb:386-396`).
- [code] **Reopen on contact message** is a callback on the *message*, not the conversation: `after_create_commit` (`app/models/message.rb:141`) runs `execute_after_create_commit_callbacks` (`app/models/message.rb:333-342`), which calls `reopen_conversation` first (`app/models/message.rb:414-421`). An incoming message reopens a snoozed conversation and, for a resolved one, either sets `pending` (inbox has an active bot) or `open` (`app/models/message.rb:435-445`). Muted conversations (blocked contact) are not reopened (`app/models/message.rb:415`). [doc] The API description says snoozed conversations always reopen on the next contact reply (`swagger/paths/application/conversation/toggle_status.yml:9-11`). Specs: `spec/models/message_spec.rb:253-286`, `spec/models/conversation_spec.rb:374-398`.
- [code] Activity timestamps: `last_activity_at` is written by the message callback with `update_columns` (`app/models/conversation.rb:164-166`, `app/models/message.rb:459-463`); `waiting_since` starts at `created_at` (`app/models/conversation.rb:298-300`), is set on an incoming message when blank and cleared on a human or bot reply (`app/models/message.rb:348-369`); `first_reply_created_at` is set when the first qualifying human reply is created (`app/models/message.rb:232-242`, `app/models/message.rb:389-398`). Specs: `spec/models/message_spec.rb:157-185`, `spec/models/message_spec.rb:297-300`.
- [code] Relations: a conversation belongs to account, inbox, optional assignee user, optional polymorphic AI assignee, contact, contact_inbox, optional team and optional campaign; it has many messages and participants, both `dependent: :destroy_async` (`app/models/conversation.rb:114-130`). A `contact_inbox` is the contact's identity inside one inbox, unique per `(inbox_id, source_id)` (`db/schema.rb:788-801`, `db/schema.rb:797`).
- [code] Which conversation a visitor writes to: the widget uses the contact's *last* conversation (`app/controllers/api/v1/widget/base_controller.rb:20-22`); the API builder reuses `contact_inbox.conversations.last` only if the inbox has `lock_to_single_conversation` (`app/builders/conversation_builder.rb:10-14`, `db/schema.rb:1355`).
- [inference] Lifecycle logic is spread across the conversation model, the message model, controllers and jobs; there is no single function that owns a status transition.

## 2. Message schema and sender identity

- [code] The `messages` table: `content` text, `account_id`, `inbox_id`, `conversation_id` (all NOT NULL integers), `message_type`, `private`, `status`, `source_id` text, `content_type`, `content_attributes` json, polymorphic `sender_type` + `sender_id`, `external_source_ids` jsonb, `additional_attributes` jsonb, `processed_message_content` (`db/schema.rb:1443-1461`). The primary key is a serial integer; there is **no** per-conversation sequence column.
- [code] `message_type` is `incoming 0 / outgoing 1 / activity 2 / template 3`; `content_type` has 13 values (text, input forms, cards, article, incoming_email, csat, sticker, voice_call and others); delivery `status` is `sent 0 / delivered 1 / read 2 / failed 3` (`app/models/message.rb:88-104`). Content is capped at 150,000 characters (`app/models/message.rb:80`).
- [code] Sender identity is a polymorphic pair that is optional (`app/models/message.rb:135`). Observed sender classes in code: agent `User`, `Contact`, `AgentBot` and `Captain::Assistant` (`app/models/message.rb:236`, `app/models/message.rb:377-387`); `Captain::Assistant` is defined under the Enterprise tree (`enterprise/app/models/captain/assistant.rb:1` [EE-LICENCE]). The agent-side builder chooses an explicit AgentBot or the current user for outgoing and the conversation's contact otherwise (`app/builders/messages/message_builder.rb:135-137`, `app/builders/messages/message_builder.rb:155-159`); the widget always sets `sender: @contact` and `message_type: :incoming` (`app/controllers/api/v1/widget/base_controller.rb:79-91`).
- [code] The message model only validates that `account_id`, `inbox_id`, `conversation_id` are present (`app/models/message.rb:71-73`); the callers copy `account_id` and `inbox_id` from the conversation (`app/builders/messages/message_builder.rb:161-165`, `app/controllers/api/v1/widget/base_controller.rb:79-91`). [inference] Tenant consistency of a message row depends on every caller doing that copy.
- [code] Free-form extras go into a JSON `content_attributes` store with typed accessors (`in_reply_to`, `deleted`, `external_created_at`, `is_unsupported`, translations and others) (`app/models/message.rb:105-116`).
- [code] Private notes are a boolean on the message (`db/schema.rb:1451`). They are excluded from the contact-facing stream (`app/listeners/action_cable_listener.rb:211-217`), from the `chat` scope (`app/models/message.rb:121`) and from the widget message list (`app/finders/message_finder.rb:19-23`).
- [code] Activity messages (`message_type: activity`) record status, assignee, priority and label changes in the timeline; they are created by a background job, not in the transaction that changed the conversation (`app/models/concerns/activity_message_handler.rb:12-19`, `app/models/concerns/activity_message_handler.rb:50-71`, `app/jobs/conversations/activity_message_job.rb:1-7`).
- [code] Flood control: each message insert runs a `COUNT` of that conversation's messages in the last minute against a limit (default 200) (`app/models/message.rb:297-307`, `lib/limits.rb:13-15`).
- [code] Delivery status moves forward only, under a row lock; `failed` can be entered or left from any state (`app/services/messages/status_update_service.rb:10-18`, `app/services/messages/status_update_service.rb:36-45`).

## 3. Message idempotency

- [code] **No client message id is persisted.** `echo_id` is a non-persisted accessor on the model (`app/models/message.rb:83-84`) that is copied into the push payload (`app/models/message.rb:157`). The agent-side builder passes both `echo_id` and `source_id` from request parameters straight into the new message (`app/builders/messages/message_builder.rb:173-174`); the widget endpoint permits `echo_id` only (`app/controllers/api/v1/widget/messages_controller.rb:83-93`, `app/controllers/api/v1/widget/base_controller.rb:88`).
- [doc] The API reference describes `echo_id` as a temporary identifier passed back via websockets (`swagger/definitions/request/public/message/create_payload.yml:7-10`). It is an echo for UI reconciliation, not an idempotency key.
- [code] The widget create endpoint is a plain `save!` with no lookup for an earlier identical request (`app/controllers/api/v1/widget/messages_controller.rb:10-14`); the agent endpoint builds and saves the same way (`app/controllers/api/v1/accounts/conversations/messages_controller.rb:8-14`, `app/builders/messages/message_builder.rb:24-33`). [inference] A client retry after a timeout creates a second message.
- [code] The widget JavaScript does not even send `echo_id`: the request carries content, reply_to, timestamp and referer only (`app/javascript/widget/api/endPoints.js:26-36`). It creates a temporary message with a random UUID and status `in_progress` (`app/javascript/widget/store/modules/conversation/helpers.js:5-16`), then replaces it by finding a pending message with the **same content** (`app/javascript/widget/store/modules/conversation/helpers.js:46-49`, `app/javascript/widget/store/modules/conversation/mutations.js:22-34`). The dashboard does send `echo_id` and matches on it or on the id (`app/javascript/dashboard/helper/commons.js:46-61`, `app/javascript/dashboard/store/modules/conversations/helpers.js:33-38`).
- [code] `source_id` (the provider's message id) has a **non-unique** index (`db/schema.rb:1474`). Deduplication of inbound provider events is check-then-insert: WhatsApp looks the id up and then takes a Redis `SET NX` lock with a one-day TTL (`app/services/whatsapp/incoming_message_base_service.rb:34-39`, `app/services/whatsapp/incoming_message_service_helpers.rb:99-103`, `app/services/whatsapp/message_dedup_lock.rb:5-19`); Instagram and email do a plain lookup (`app/builders/messages/instagram/base_message_builder.rb:175-183`, `app/mailboxes/mailbox_helper.rb:8-14`). [inference] A lost or expired Redis key, or two workers racing the lookup, can still insert duplicates because no database constraint backs it. The Redis key is `MESSAGE_SOURCE_KEY::<id>` with no tenant prefix (`lib/redis/redis_keys.rb:77`).
- [code] Where the database does enforce uniqueness, creation is retried safely: contact_inbox is created with `first_or_create!`, rescues `RecordNotUnique` and retries (`app/builders/contact_inbox_builder.rb:61-73`), backed by the unique `(inbox_id, source_id)` index (`db/schema.rb:797`).
- [code] Retrying an *outbound* failed message is claimed under a row lock so concurrent retries send once (`app/controllers/api/v1/accounts/conversations/messages_controller.rb:30-34`, `app/controllers/api/v1/accounts/conversations/messages_controller.rb:75-83`).
- [code, comment] The Instagram job's own comment says its lock is only a short race dampener and that concurrent first messages can create duplicate conversations (`app/jobs/webhooks/instagram_events_job.rb:3-7`).

## 4. Ordering and pagination

- [code] Messages carry a `default_scope` ordered by `created_at` ascending (`app/models/message.rb:127-130`). The main per-conversation index is `(conversation_id, account_id, message_type, created_at)` (`db/schema.rb:1468`).
- [code] There is no sequence, version or monotonic counter on `messages` or `conversations` (`db/schema.rb:990-1038`, `db/schema.rb:1443-1475`). Not found.
- [code] `MessageFinder` pages with the **integer primary key as the cursor but `created_at` as the sort key**: latest 20 reversed (`app/finders/message_finder.rb:56-58`), `before` returns 20 rows with `id < cursor` (`app/finders/message_finder.rb:43-48`), `after` returns up to 100 rows with `id > cursor` (`app/finders/message_finder.rb:39-41`), and a bounded range returns up to 1000 (`app/finders/message_finder.rb:50-54`). Ids are clamped to the integer maximum (`app/finders/message_finder.rb:2`, `app/finders/message_finder.rb:60-66`). [inference] When `id` order and `created_at` order disagree (two concurrent inserts, timestamps with equal values) a page can skip or repeat a row; there is no tie-breaker on messages.
- [code, comment] The conversation model warns that the timestamp columns may be stored with lower precision than Ruby times (`app/models/conversation.rb:158-166`). [inference] I did not verify the database precision; the schema shows `precision: nil` (`db/schema.rb:995`).
- [code] The conversation list is sorted by `last_activity_at` by default and uses offset pagination with 25 per page (`app/models/concerns/sort_handler.rb:5-7`, `app/finders/conversation_finder.rb:206`). The `created_at` sort adds an `id` tie-breaker, with a comment that this keeps pagination stable (`app/models/concerns/sort_handler.rb:9-12`).
- [code, comment] Event ordering is acknowledged as weak: the broadcast job comments that out-of-order events happen under heavy traffic and, for conversation events, re-reads the latest conversation state before broadcasting (`app/jobs/action_cable_broadcast_job.rb:22-43`). The Instagram job comments that job retries are not first-in-first-out (`app/jobs/webhooks/instagram_events_job.rb:8-11`). [inference] No per-conversation ordering guarantee exists between jobs on the shared Sidekiq queues (`config/sidekiq.yml:17-35`).

## 5. Read / unread

- [code] Read state is three **per-conversation** timestamps: `contact_last_seen_at`, `agent_last_seen_at` and `assignee_last_seen_at` (`db/schema.rb:999-1000`, `db/schema.rb:1010`). `agent_last_seen_at` is shared by every agent: it records "some agent looked", not who.
- [code] The agent mark-read endpoint writes the wall-clock time with `update_columns` (no validations, no callbacks) and also updates the assignee cursor when the caller is the assignee (`app/controllers/api/v1/accounts/conversations_controller.rb:113-126`, `app/controllers/api/v1/accounts/conversations_controller.rb:153-160`, `app/controllers/api/v1/accounts/conversations_controller.rb:235-237`). When nothing is unread, the write is throttled to once per hour to cut database load (`app/controllers/api/v1/accounts/conversations_controller.rb:114-123`, `app/controllers/api/v1/accounts/conversations_controller.rb:165-174`). "Mark unread" sets the cursor one second before the last incoming message (`app/controllers/api/v1/accounts/conversations_controller.rb:128-132`).
- [code] Unread is derived by time comparison: messages created after the cursor (`app/models/conversation.rb:199-205`), the last 10 unread incoming messages (`app/models/conversation.rb:207-209`), and a correlated SQL count used to sort by unread (`app/models/conversation.rb:239-257`). The push payload includes an unread count computed on every broadcast (`app/presenters/conversations/event_data_presenter.rb:16`, `app/models/message.rb:162-169`). [inference] Because `last(10)` returns an array, that `count` is capped at 10.
- [code] Contact side: the widget's mark-read sets `contact_last_seen_at` to now and enqueues a job that marks outgoing messages created up to that time as `read` (`app/controllers/api/v1/widget/conversations_controller.rb:28-35`, `app/jobs/conversations/update_message_status_job.rb:7-21`). The `conversation.read` event fires only for a change of the contact cursor (`app/models/conversation.rb:391`).
- [code] A Redis-backed unread counter subsystem exists behind account feature flags, with TTLs and invalidators (`app/services/conversations/unread_counts.rb:1-10`, `app/services/conversations/unread_counts/store.rb:1-30`, `app/services/conversations/unread_counts/listener.rb:10-21`).
- [code] `conversation_participants` has **no** read-cursor column (`db/schema.rb:978-988`). Per-participant read cursors: not found.
- [doc] The API reference says the endpoint "updates the last seen of the conversation" so agents see unread bubbles (`swagger/paths/application/conversation/update_last_seen.yml:8`).
- Specs: `spec/models/conversation_spec.rb:619-642`, `spec/models/conversation_spec.rb:668-698`.

## 6. Assignment and participants

- [code] Assignment columns on the conversation: `assignee_id`, `team_id`, and an AI assignee stored as `assignee_agent_bot_id` plus `ai_assignee_type` (`db/schema.rb:994`, `db/schema.rb:1006`, `db/schema.rb:1016-1017`; model `app/models/conversation.rb:117-121`, `app/models/conversation.rb:223-233`).
- [code] Manual assignment: `Conversations::AssignmentService` takes a row lock, moves a bot-owned `pending` conversation to `open` when a human is assigned, sets the assignee and saves (`app/services/conversations/assignment_service.rb:16-27`); assigning a bot forces `pending` (`app/services/conversations/assignment_service.rb:37-47`). The assignee is looked up among the account's users only (`app/services/conversations/assignment_service.rb:49-51`). Team assignment also locks the row (`app/controllers/api/v1/accounts/conversations/assignments_controller.rb:36-43`).
- [code] **Auto-assignment lives inside the conversation model's callbacks**: a `before_save` runs the legacy path inside the same save so status and assignee commit together (`app/models/concerns/auto_assignment_handler.rb:5-22`), an `after_save` runs the post-create or V2 path (`app/models/concerns/auto_assignment_handler.rb:24-41`), and a team change auto-picks an assignee (`app/models/concerns/assignment_handler.rb:5-29`). Assignment events and activity messages are emitted from `after_commit` (`app/models/concerns/assignment_handler.rb:31-53`).
- [code] Strategies: V1 is a per-inbox Redis list round robin restricted to agents that Redis presence marks online (`app/services/auto_assignment/inbox_round_robin_service.rb:29-33`, `app/services/auto_assignment/agent_assignment_service.rb:61-72`, `lib/online_status_tracker.rb:3-14`). V2 is a per-inbox bulk job, coalesced by a Redis in-flight key with a token (`app/jobs/auto_assignment/assignment_job.rb:6-23`), that claims each conversation with a `FOR UPDATE SKIP LOCKED` transaction (`app/services/auto_assignment/assignment_service.rb:107-122`), plus a 30-minute periodic job (`config/schedule.yml:76-80`). `assign_under_lock` re-reads the row under lock and drops a status change another writer already committed (`app/services/auto_assignment/agent_assignment_service.rb:11-28`, `app/services/auto_assignment/agent_assignment_service.rb:40-48`).
- [code] Participants: a table with unique `(user_id, conversation_id)` and `account_id` (`db/schema.rb:978-988`); a participant must have inbox access (`app/models/conversation_participant.rb:19-24`, `app/models/conversation_participant.rb:39-41`); add and remove run in a transaction (`app/controllers/api/v1/accounts/conversations/participants_controller.rb:10-31`); the assignee is auto-added by a listener that swallows uniqueness races (`app/listeners/participation_listener.rb:4-14`). Participants are agents only (`user_id NOT NULL`), not customers.
- [code] Inbox membership and teams decide who can be assigned and who receives events (`db/schema.rb:1328-1335`, `db/schema.rb:1690-1710`). Capacity limits and balanced assignment live under `enterprise/` (`enterprise/app/services/enterprise/auto_assignment/assignment_service.rb:17-35` [EE-LICENCE]).
- [inference] Chatwoot couples status, assignment, notification and activity logic in one aggregate. Our direction (assignment owned by a separate allocation service) means we would keep only the *command surface* (assign, unassign) and the locking discipline, not the in-model callbacks.

## 7. Archive, resolve, reopen and deletion

- **Archive: not found.** `grep -ri archiv` over `app/models`, `app/controllers`, `app/services`, `app/finders`, `app/jobs` and `db/schema.rb` matched help-centre articles and portals (`db/schema.rb:1559`, `db/schema.rb:1571`) and the Freshdesk importer, which copies the *source ticket's* `archived` flag into import metadata (`app/services/data_imports/freshdesk/metadata.rb:32`, `app/services/data_imports/freshdesk/normalizer.rb:98`); that is a foreign system's attribute, not a Chatwoot conversation state. Neither conversations nor messages have an archive concept. The nearest things are `resolved` and mute.
- [code] Resolve and auto-resolve: a cron job every five minutes (overridable) loops over accounts with auto-resolve configured, and a per-account job resolves open conversations idle past the threshold (at most 100 per run) via `toggle_status` (`config/schedule.yml:23-26`, `app/jobs/account/conversations_resolution_scheduler_job.rb:4-8`, `app/jobs/conversations/resolution_job.rb:4-16`, `app/models/conversation.rb:96-105`). A web-widget visitor can resolve their own conversation when the widget allows it (`app/controllers/api/v1/widget/conversations_controller.rb:57-65`), and an inbox flag can forbid replies to a resolved conversation (`app/controllers/api/v1/widget/messages_controller.rb:46-53`, `db/schema.rb:1353`).
- [code] Snooze: `snoozed_until` plus a scheduled job reopening conversations whose time has passed within a three-day window (`app/jobs/conversations/reopen_snoozed_conversations_job.rb:4-6`, `app/jobs/trigger_scheduled_items_job.rb:11-12`, `config/schedule.yml:17-20`).
- [code] Mute is **resolve plus block the contact**: `mute!` resolves the conversation and sets `blocked` on the contact (`app/models/concerns/conversation_mute_helpers.rb:4-10`); a muted conversation is not reopened by new messages (`app/models/message.rb:415`).
- [code] Conversation deletion is a hard delete: administrator-only (`app/policies/conversation_policy.rb:6-8`), enqueued as a low-priority job that calls `destroy!` (`app/controllers/api/v1/accounts/conversations_controller.rb:134-138`, `app/services/conversations/delete_service.rb:4-7`, `app/jobs/delete_object_job.rb:2-11`), with messages and participants destroyed asynchronously as dependents (`app/models/conversation.rb:127-134`) and a deletion event built from a snapshot taken before destroy (`app/models/conversation.rb:145-146`, `app/models/conversation.rb:340-344`, `app/models/conversation.rb:404-413`). There is no soft-delete column (`db/schema.rb:990-1038`). Spec: `spec/models/conversation_spec.rb:825-857`.
- [code] Message deletion is a **tombstone**: in one transaction the content is replaced by a localized "deleted" text, `deleted: true` is written into `content_attributes`, and attachments are destroyed (`app/controllers/api/v1/accounts/conversations/messages_controller.rb:21-28`). The widget filters deleted messages out when syncing (`app/javascript/widget/store/modules/conversation/helpers.js:51-55`). Enterprise adds a `not_deleted` scope (`enterprise/app/models/enterprise/concerns/message.rb:8-9` [EE-LICENCE]).
- [code] Housekeeping: conversations whose contact was deleted are destroyed in batches of 1000 every 12 hours (`app/services/internal/remove_orphan_conversations_service.rb:7-22`, `config/schedule.yml:89-94`).

## 8. Realtime event contracts

## 13. Transaction boundaries and concurrency

- [code] The effects of a new message are `after_create_commit` callbacks: reopen, activity timestamp, event dispatch, outbound send enqueue, template hooks, contact activity (`app/models/message.rb:141`, `app/models/message.rb:333-342`). Each does its own separate write (`app/models/message.rb:358`, `app/models/message.rb:368`, `app/models/message.rb:394`, `app/models/message.rb:459-463`). [inference] They run after the message row has committed, so a failure inside them does not roll back the message and can leave a message stored but the conversation not reopened or the event not sent.
- [code] Explicit transactions wrap creation of a conversation together with its first message (`app/controllers/api/v1/accounts/conversations_controller.rb:41-46`, `app/controllers/api/v1/widget/conversations_controller.rb:9-17`) and message tombstoning (`app/controllers/api/v1/accounts/conversations/messages_controller.rb:21-28`). Posting a message to an existing widget conversation is a bare `save!` (`app/controllers/api/v1/widget/messages_controller.rb:10-14`).
- [code] Pessimistic locks are used for assignment (`app/services/conversations/assignment_service.rb:17`, `app/services/conversations/assignment_service.rb:40`), team change (`app/controllers/api/v1/accounts/conversations/assignments_controller.rb:39`), human takeover (`app/controllers/api/v1/accounts/conversations_controller.rb:181-187`), message status (`app/services/messages/status_update_service.rb:13-18`), failed-message retry (`app/controllers/api/v1/accounts/conversations/messages_controller.rb:75-83`) and auto-assignment (`app/services/auto_assignment/agent_assignment_service.rb:15-28`, `app/services/auto_assignment/assignment_service.rb:109-122`). Inserting a message takes no explicit lock on the conversation row; the conversation is touched afterwards by separate `UPDATE`s from the after-commit callbacks (`app/models/message.rb:459-463`). Optimistic locking: not found (`grep lock_version db/schema.rb` returned nothing).
- [code] Event emission is tied to Active Record commit callbacks and then to Sidekiq: `after_update_commit` and `after_create_commit` on conversation (`app/models/conversation.rb:142-146`), `after_commit` on assignment (`app/models/concerns/assignment_handler.rb:7`). Enqueuing the assignment job is deferred with `after_all_transactions_commit` so the job can see committed data (`app/models/concerns/auto_assignment_handler.rb:30-35`). [inference] Events are enqueued to Redis-backed Sidekiq or published to Redis pub/sub *after* the database commit, in a different system, with no stored record of the event: a crash or Redis outage between commit and enqueue loses the event. That is the gap a transactional outbox closes.
- [code, comment] Race conditions are handled case by case and documented in comments: a duplicate `conversation.opened` if a concurrent writer committed the same transition (`app/services/auto_assignment/agent_assignment_service.rb:40-48`), participant creation races (`app/listeners/participation_listener.rb:9-14`), the Instagram first-message race (`app/jobs/webhooks/instagram_events_job.rb:3-7`), and a Redis lock whose unlock is not owner-checked (`app/jobs/mutex_application_job.rb:25-29`). The `before_save` auto-assignment exists because a second save would erase `saved_changes` that later callbacks read (`app/models/concerns/auto_assignment_handler.rb:12-14`).
