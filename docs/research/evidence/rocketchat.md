## 1. Conversation identity and lifecycle

- [code] The conversation container is a Room; an omnichannel conversation is a room whose type is `'l'` (`packages/core-typings/src/IRoom.ts:243-244`, `packages/core-typings/src/IRoom.ts:382`). The room carries denormalised activity data: a message counter `msgs`, a last-message time `lm` and an embedded `lastMessage` copy (`packages/core-typings/src/IRoom.ts:16`, `packages/core-typings/src/IRoom.ts:38-39`).
- [code] Ids are strings. The base model generates an ObjectId hex string when the caller supplies none (`packages/models/src/models/BaseRaw.ts:301-305`). A new livechat room takes its id from the caller or from `Random.id()` and is created with `msgs: 0`, `open: true` and `waitingResponse: true` (`apps/meteor/server/lib/omnichannel/QueueManager.ts:289-295`, `apps/meteor/server/lib/omnichannel/Helper.ts:116-135`).
- [code] There is **no single status field** for an omnichannel conversation. Its state is spread over the room (`open` flag, `closedAt`, `servedBy`, `onHold`, and an optional `status` of queued / taken / ready that a source comment flags as lacking proper types) and over a second record, the inquiry, whose own status enum is verifying / queued / taken / ready / open (`packages/core-typings/src/IRoom.ts:52`, `packages/core-typings/src/IRoom.ts:266-272`, `packages/core-typings/src/IRoom.ts:277`, `packages/core-typings/src/IRoom.ts:303`, `packages/core-typings/src/IInquiry.ts:9-15`).
- [code] Room and inquiry are created together inside one MongoDB multi-document transaction, retried up to three more times on transient transaction errors (`apps/meteor/server/lib/omnichannel/QueueManager.ts:248-287`, `apps/meteor/server/database/utils.ts:22-24`). A comment says this is meant to prevent rooms without inquiries and the reverse (`apps/meteor/server/lib/omnichannel/QueueManager.ts:371-373`). Everything after that (the "livechat-started" system message, app events, queue processing) runs outside the transaction (`apps/meteor/server/lib/omnichannel/QueueManager.ts:375-394`).
- [code] The inquiry's first status is computed from settings and context: verifying when contact verification is required, queued when a waiting queue is enabled or no agent was chosen, ready when a bot or auto-assign routing can take it directly (`apps/meteor/server/lib/omnichannel/QueueManager.ts:130-167`).
- [code] One open livechat room per visitor is enforced by a partial **unique** index on the visitor token for open rooms that carry a marker field, so that old duplicate data does not block index creation (`packages/models/src/models/LivechatRooms.ts:77-85`, `apps/meteor/server/lib/omnichannel/Helper.ts:147-149`). When the visitor's room is missing or closed, the next visitor message creates a new room; a different visitor's token is rejected (`apps/meteor/server/lib/omnichannel/rooms.ts:49-83`).
- [code] Reopening a closed omnichannel room exists on one path only, the inbound-email path: if the thread's room has `closedAt`, `QueueManager.unarchiveRoom` is called (`apps/meteor/server/features/EmailInbox/EmailInbox_Incoming.ts:135-137`). It deletes the old inquiry, sets `open: true`, unsets `servedBy`, `closedAt`, `closedBy` and `closer`, creates a fresh inquiry and re-queues it, preferring the previous agent if online (`apps/meteor/server/lib/omnichannel/QueueManager.ts:419-478`, `packages/models/src/models/LivechatRooms.ts:2426-2444`). In spite of the name this is a reopen, not the `archived` flag (Section 7).
- [code] The queue worker has a reconciliation step for three room/inquiry mismatches: inquiry whose room is missing, inquiry whose room already has `servedBy`, and inquiry whose room is closed (`apps/meteor/server/services/omnichannel/queue.ts:184-226`, `apps/meteor/server/services/omnichannel/queue.ts:234-253`); unit tests exist for each (`apps/meteor/server/services/omnichannel/queue.test.ts:241-270`). Comments on the three checks describe each as a precaution or safety net for a case that should not happen (`apps/meteor/server/services/omnichannel/queue.ts:236-237`, `apps/meteor/server/services/omnichannel/queue.ts:243`, `apps/meteor/server/services/omnichannel/queue.ts:249`).
- [code] On-hold exists as a room flag, but the community model throws a not-implemented error when asked to set it; the working implementation is Enterprise (`packages/models/src/models/LivechatRooms.ts:2586-2592`, `apps/meteor/ee/server/models/raw/LivechatRooms.ts:107-113` [EE-LICENCE]).
- [inference] Lifecycle meaning has to be reconstructed from four room fields plus an inquiry record in a different collection, and the code base ships a reconciler for the cases where they disagree, although its own comments treat those cases as precautions rather than routine events, so how often they occur is unknown. Splitting state over two records is what makes such a check necessary. For us this argues for one conversation row with an explicit status enum and an assignment projection, not a second queue record.

## 2. Message schema and sender identity

- [code] A message record has `_id`, `_updatedAt`, `rid` (room), `msg` (text), `ts` (creation time), `u` (sender), optional `t` (system message type), `tmid` / `tshow` (thread), `_hidden`, `unread`, `attachments` / `files`, `reactions`, `editedAt` / `editedBy` and more (`packages/core-typings/src/IMessage/IMessage.ts:146-226`, `packages/core-typings/src/IRocketChatRecord.ts:6-9`). There is no tenant field and no per-room sequence field (Sections 4 and 10).
- [code] Sender identity is an **embedded snapshot** `u = { _id, username, name }` written by the server from the authenticated user (`apps/meteor/server/lib/messages/sendMessage.ts:203-209`). A visitor is recognised by the presence of a `token` field on the message (`packages/core-typings/src/IMessage/IMessage.ts:410-414`); the omnichannel send path stamps the visitor token and display name onto each message (`apps/meteor/server/lib/omnichannel/messages.ts:149`).
- [inference] The visitor token is a bearer secret (it authenticates the visitor endpoints, `apps/meteor/server/api/v1/omnichannel/message.ts:29-38`), so every visitor message row stores a copy of that secret.
- [code] System messages share the collection and carry a `t` type (`packages/core-typings/src/IMessage/IMessage.ts:269-271`, `packages/core-typings/src/IMessage/IMessage.ts:287-288`). `saveSystemMessage` inserts the row and, in parallel, increments the room's message counter, then notifies; it does not go through the user send pipeline (`apps/meteor/server/services/messages/service.ts:181-230`).
- [code] Creation time `ts` comes from the server (`new Date()`) unless the caller sent one (`apps/meteor/server/lib/messages/sendMessage.ts:195-197`). In the outer command a client-sent `ts` is accepted if within 10 s of the server clock, replaced by the server clock between 10 s and 60 s, and rejected beyond 60 s (`apps/meteor/server/meteor-methods/messages/sendMessage.ts:42-57`).
- [code] Maximum length is the setting `Message_MaxAllowedSize`, default 5000 (`apps/meteor/server/settings/message.ts:168`). It is enforced in the outer command only (`apps/meteor/server/meteor-methods/messages/sendMessage.ts:59-65`); the inner `sendMessage` documents that it does not check the limit and leaves it to callers (`apps/meteor/server/lib/messages/sendMessage.ts:220-223`). The livechat visitor endpoint has its own optional character limit (`apps/meteor/server/api/v1/omnichannel/message.ts:45-50`).
- [code] Validation uses Meteor `check` / `Match` on a whitelist of fields, rejects `javascript:` URL values (and, for most link fields, anything that is not an absolute URL), and requires the `message-impersonate` permission for `alias` / `avatar` unless the sender is the room's livechat guest (`apps/meteor/server/lib/messages/sendMessage.ts:33-59`, `apps/meteor/server/lib/messages/sendMessage.ts:152-175`). The REST schema declares which message fields a caller may set, and `chat.sendMessage` reports or rejects the rest (`packages/rest-typings/src/v1/chat.ts:36-148`, `apps/meteor/server/api/v1/chat.ts:937-958`).
- [code] `sendMessage` versus `insertMessage`: `sendMessage` is the full pipeline (validate, prepare, optional app pre-events, `Message.beforeSave`, insert or upsert, app post-events, `afterSaveMessage` hooks, room notification) (`apps/meteor/server/lib/messages/sendMessage.ts:225-298`). `insertMessage` is a lower-level insert that validates, parses URLs, inserts (or upserts by `_id`) and bumps the room counter, with a TODO to move it into the message service; it skips the hooks and notifications and is used by the importer (`apps/meteor/server/lib/messages/insertMessage.ts:7-48`, `apps/meteor/server/lib/import/classes/converters/MessageConverter.ts:82`).
- [code] `Message.beforeSave` is a fixed list of transforms: federation guard, canned-response placeholders, bad-word filter, markdown parse, mention resolution, URL parsing, Spotify and quote attachments, then a monthly-active-contacts limit and `@all` / `@here` permission checks for fresh, non-edited messages (`apps/meteor/server/services/messages/service.ts:232-284`).
- [code] The messages collection is indexed for room history by `{ rid, ts, _updatedAt }`; the model declares 25 indexes in all, many of them sparse, partial or TTL, plus a text index managed at startup (`packages/models/src/models/Messages.ts:41-77`).

## 3. Message idempotency

- [code] There is **no dedicated client message id field**. The nearest thing is the message `_id`: the REST schema for `chat.sendMessage` accepts an optional `_id` string (`packages/rest-typings/src/v1/chat.ts:41-44`), `validateMessage` accepts `_id` (`apps/meteor/server/lib/messages/sendMessage.ts:155-157`), and the base model keeps a caller-supplied string `_id` instead of generating one (`packages/models/src/models/BaseRaw.ts:301-305`). The livechat visitor endpoint does `this.bodyParams._id || Random.id()` (`apps/meteor/server/api/v1/omnichannel/message.ts:52`).
- [code] Duplicate handling in `sendMessage` is **check, then insert**: if a message with that `_id` already exists the function returns early with no result; otherwise it inserts (`apps/meteor/server/lib/messages/sendMessage.ts:278-285`). The existence check does not compare the sender or the room.
- [code] An `upsert` variant exists: when `_id` is present and `upsert` is set it does an update-with-upsert filtered on both `_id` and the sender id, so a user can only overwrite their own message (`apps/meteor/server/lib/messages/sendMessage.ts:266-277`). It is reached through the message service wrapper and by the importer (`apps/meteor/server/services/messages/service.ts:146-148`, `apps/meteor/server/lib/messages/insertMessage.ts:22-40`).
- [code] The livechat visitor endpoint sends, then re-reads the message by the same `_id`, and the omnichannel wrapper spreads the send result into its return value even when the inner send returned nothing (`apps/meteor/server/api/v1/omnichannel/message.ts:70-76`, `apps/meteor/server/lib/omnichannel/messages.ts:147-153`).
- [inference] A visitor retrying with the same `_id` therefore gets the stored message back, which behaves like an idempotent send on that path. It is a side effect of the wrapper shape rather than a stated contract, and I found no test for it.
- [inference] On the authenticated REST path (`chat.sendMessage`) a duplicate client `_id` probably errors instead of returning the stored message: the early return yields no message, and the route passes that result to `normalizeMessagesForUser`, which reads fields of each message it is given (`apps/meteor/server/api/v1/chat.ts:968-971`, `apps/meteor/server/lib/utils/lib/normalizeMessagesForUser.ts:8-14`). Not exercised; not found: a test that sends the same `_id` twice.
- [inference] Because `_id` is the primary key of the whole collection and the early return does not check ownership, a client-chosen id that collides with another sender's message id is silently dropped; uniqueness is global, not per conversation or per sender. The existence check is not atomic with the insert, so a concurrent duplicate would be stopped by the primary-key constraint and surface as an error rather than a no-op (not exercised).
- [code] Inbound email is deduplicated differently: the email's `Message-ID` is inserted as the primary key of a small history collection, and only if that insert succeeds is the email processed; a duplicate insert throws and is logged. The collection has a TTL index of one day (`apps/meteor/server/features/EmailInbox/EmailInbox.ts:59-71`, `packages/models/src/models/EmailMessageHistory.ts:12-14`).
- [inference] Claim-first dedupe makes duplicate suppression database-enforced, which is the right idea. But the claim and the message creation are separate writes (`apps/meteor/server/features/EmailInbox/EmailInbox.ts:65-66`), so a failure between them loses the email, and the one-day TTL bounds how long a duplicate can be recognised.
- [code] Not found: a test that sends the same message `_id` twice, searched in `apps/meteor/tests/end-to-end/api/chat.ts`, `apps/meteor/tests/end-to-end/api-livechat/00-rooms.ts` and `apps/meteor/tests/end-to-end/api-livechat/20-messages.ts` for `same id`, `same _id`, `already exist`, `twice` and `duplicate`.
- [code] Abuse control on send is a rate limit on the REST route: 5 requests per second unless the caller has `send-many-messages` (`apps/meteor/server/api/v1/chat.ts:920`).

## 4. Ordering and pagination

- [code] Not found: any per-conversation sequence number. A search for `sequence`, `seq`, `seqNo` and `seqnum` over `packages/core-typings/src/IMessage/`, `packages/core-typings/src/IRoom.ts`, `packages/core-typings/src/ISubscription.ts`, `packages/core-typings/src/IInquiry.ts`, `apps/meteor/server/lib/messages/` and `apps/meteor/server/api/v1/chat.ts` returned nothing. The only counter is the room's `msgs`, which is incremented but not stamped on messages (`packages/models/src/models/Rooms.ts:890-896`).
- [code] Order is by creation timestamp `ts`, a millisecond wall-clock value set by the application server (`apps/meteor/server/lib/messages/sendMessage.ts:195-197`).
- [code] The older loader `loadMessageHistory` sorts by `ts` descending and pages with `limit` plus `skip: offset`, optionally bounded by an `end` date (`apps/meteor/server/lib/messages/loadMessageHistory.ts:39-55`). The livechat visitor history endpoint still uses it (`apps/meteor/server/api/v1/omnichannel/message.ts:223-240`).
- [code] The newer loader `loadRoomHistory`, behind `rooms.history`, uses a cursor that **is the `ts` as epoch milliseconds** (`apps/meteor/server/lib/messages/loadRoomHistory.ts:25-27`). `next`, `previous` and `around` are mutually exclusive (`apps/meteor/server/lib/messages/loadRoomHistory.ts:68-70`); it fetches `count + 1` rows to learn whether another page exists (`apps/meteor/server/lib/messages/loadRoomHistory.ts:119-120`, `apps/meteor/server/lib/messages/loadRoomHistory.ts:141-145`) and returns `{ messages, cursor: { next, previous }, firstUnread, unreadNotLoaded }` newest first (`apps/meteor/server/lib/messages/loadRoomHistory.ts:43-94`). The endpoint caps `count` through the global upper limit, defaults to 20 and is rate limited to 20 calls per 10 s (`apps/meteor/server/api/v1/rooms.ts:1770-1784`).
- [code] **What the tiebreak really does.** A comment in the loader says an in-memory `_id` tie-break is applied for equal `ts` because the `{ rid, ts, _updatedAt }` index cannot back a `{ ts, _id }` sort (`apps/meteor/server/lib/messages/loadRoomHistory.ts:96-100`). The tie-break only orders rows inside the fetched window; the cursor carries no `_id` (`apps/meteor/server/lib/messages/loadRoomHistory.ts:83-86`), and the underlying queries use strict `$lt` / `$gt` bounds unless `inclusive` is passed (`packages/models/src/models/Messages.ts:906-923`, `packages/models/src/models/Messages.ts:944-963`).
- [inference] Messages that share the exact millisecond of a page boundary can be skipped when paging, and two application servers with different clocks can write messages whose `ts` order differs from arrival order. This is the gap a per-conversation `sequence` closes.
- [code] The unit test for the loader stubs the model and only checks the shape of the returned cursors, including that a pre-1970 timestamp never yields a negative cursor (`apps/meteor/server/lib/messages/loadRoomHistory.test.ts:9-35`).
- [code] Hidden rows are excluded from every history query with `_hidden: { $ne: true }` (`packages/models/src/models/Messages.ts:917-920`). Edit history and "keep history" deletions live as hidden clones in the same collection (Section 7).
- [code] A second cursor family syncs changes rather than history: `chat.syncMessages` pages by `_updatedAt` milliseconds, for either `UPDATED` rows or `DELETED` rows from the trash collection (`apps/meteor/server/publications/messages.ts:21-51`, `apps/meteor/server/publications/messages.ts:127-165`).

## 5. Read / unread

- [code] Read state lives on the **subscription** (one per room and user): an `unread` counter, `userMentions`, `groupMentions`, `alert`, a last-seen timestamp `ls`, and thread counters `tunread` (`packages/core-typings/src/ISubscription.ts:11-38`).
- [code] Marking a room read is `readMessages`: it runs a `beforeReadMessages` hook, sets `unread: 0`, `userMentions: 0`, `groupMentions: 0`, `alert` and `ls: new Date()` on the subscription, clears the user's notification queue, then fires `afterReadMessages` asynchronously (`apps/meteor/server/lib/readMessages.ts:7-28`, `packages/models/src/models/Subscriptions.ts:187-218`). The REST route takes only a room id (`apps/meteor/server/api/v1/subscriptions.ts:130-154`).
- [inference] `ls` is the **server wall clock at the time of the request**, not a pointer to the last message the client displayed. Messages that arrive between the client's last render and the request are marked read without being seen.
- [code] The unread counter is incremented by a **hook**, not by the send command. `notifyUsersOnMessage` runs as an `afterSaveMessage` callback, finds subscriptions of everyone except the sender, and applies `$inc` (with `alert`/`open` set) according to the settings `Unread_Count`, `Unread_Count_DM` and `Unread_Count_Omni` (default `all_messages` for DMs and omnichannel) (`apps/meteor/server/hooks/messages/notifyUsersOnMessage.ts:48-85`, `apps/meteor/server/hooks/messages/notifyUsersOnMessage.ts:87-126`, `apps/meteor/server/hooks/messages/notifyUsersOnMessage.ts:218-231`, `packages/models/src/models/Subscriptions.ts:519-540`, `apps/meteor/server/settings/general.ts:146`, `apps/meteor/server/settings/general.ts:160`). It skips counting for edited messages and for messages whose `ts` is more than 60 s from now (imports) (`apps/meteor/server/hooks/messages/notifyUsersOnMessage.ts:165-195`). The sender's own subscription is marked read at the end (`apps/meteor/server/hooks/messages/notifyUsersOnMessage.ts:144-148`).
- [code] "Mark as unread" rewinds `ls` to one millisecond before the chosen message and sets `unread: 1` (`packages/models/src/models/Subscriptions.ts:1247-1263`, `apps/meteor/server/api/v1/subscriptions.ts:156-176`).
- [code] Unread position inside a history page is computed from a client-supplied last-seen time: `firstUnread` and `unreadNotLoaded` are derived by counting visible messages between `ls` and the oldest loaded message (`apps/meteor/server/lib/messages/loadRoomHistory.ts:214-248`, `apps/meteor/server/lib/messages/loadMessageHistory.ts:58-85`).
- [code] A separate collection `MessageReads` exists, keyed by thread (`tmid`) and user with an `ls` timestamp and a unique index on `(tmid, userId)`; it serves thread read state only (`packages/core-typings/src/MessageReads.ts:6-10`, `packages/models/src/models/MessageReads.ts:12-14`, `packages/models/src/models/MessageReads.ts:33-46`). The service that uses it is Enterprise (`apps/meteor/ee/server/local-services/message-reads/service.ts:11-50` [EE-LICENCE]).
- [code] Per-message read receipts are **Enterprise**. The community build registers a dummy receipts model (`apps/meteor/server/models.ts:143`); the real model and the receipts class are under the EE tree (`apps/meteor/ee/server/models/ReadReceipts.ts:1-6` [EE-LICENCE], `apps/meteor/ee/server/lib/message-read-receipt/ReadReceipt.ts:113-127` [EE-LICENCE]). In outline, with the receipt setting on, each sent message gets `unread: true` (`apps/meteor/server/lib/messages/sendMessage.ts:235-237`), a read produces one receipt row per message and user whose `_id` is the message id plus user id, a code comment says the unique index was dropped for performance, and a 2 s per-room debounce clears the message flag once the oldest `ls` in the room passes it (`apps/meteor/ee/server/models/raw/ReadReceipts.ts:12-19` [EE-LICENCE], `apps/meteor/ee/server/lib/message-read-receipt/ReadReceipt.ts:9-37` [EE-LICENCE], `apps/meteor/ee/server/hooks/messages/afterReadMessages.ts:8-25` [EE-LICENCE]).
- [code] **Customers have no read state.** An omnichannel visitor is not a subscriber; the visitor is embedded as `v` on the room and on the agent's subscription (`packages/core-typings/src/ISubscription.ts:13`, `packages/core-typings/src/IRoom.ts:245`). The visitor history endpoint accepts `ls` straight from the query string (`apps/meteor/server/api/v1/omnichannel/message.ts:218-221`).
- [code] The agent's subscription is created at assignment with `unread: 1` and removed on transfer, unassign and close, so an agent's read state disappears with the assignment (`apps/meteor/server/lib/omnichannel/Helper.ts:295-302`, `apps/meteor/server/lib/omnichannel/Helper.ts:331-345`, `apps/meteor/server/lib/omnichannel/closeRoom.ts:195-207`).
- [code] Tests: omnichannel unread count with `Unread_Count_Omni = all_messages` (`apps/meteor/tests/end-to-end/api-livechat/00-rooms.ts:3688-3722`), and unread reset when a thread message is deleted (`apps/meteor/tests/end-to-end/api/chat.ts:2657-2700`).

## 6. Assignment and participants

- [code] Participants are subscription rows, unique per (room, user) by a **database unique index** (`packages/models/src/models/Subscriptions.ts:38`). Access to a joined room means having a subscription plus the `view-joined-room` or `view-<type>-room` permission (`packages/authorization/src/canAccessRoom.ts:74-87`).
- [code] The assignment record is a single embedded object on the room, `servedBy = { _id, ts, username }`, written by `changeAgentByRoomId`; there is no assignment history table (`packages/core-typings/src/IRoom.ts:266-270`, `packages/models/src/models/LivechatRooms.ts:2316-2332`). History is kept as a **system message** of type `livechat_transfer_history` (`apps/meteor/server/lib/omnichannel/transfer.ts:10-42`).
- [code] `assignAgent` is a sequence of independent writes: create the agent's subscription, set `servedBy`, increment the room's user count, insert two system messages, then notify (`apps/meteor/server/lib/omnichannel/RoutingManager.ts:141-173`). `createLivechatSubscription` first looks for an existing subscription and returns it, which together with the unique index makes a repeat harmless (`apps/meteor/server/lib/omnichannel/Helper.ts:288-291`).
- [code] **Take inquiry.** `takeInquiry` loads the inquiry, rejects if its status is already `taken`, requires the agent to be online, checks the contact limit and contact availability, then calls `RoutingManager.takeInquiry` (`apps/meteor/server/lib/omnichannel/takeInquiry.ts:9-64`). That function returns early if the room is closed or already served by this agent, tries an agent lock, runs the `livechat.checkAgentBeforeTakeInquiry` hook, then updates the inquiry to `taken` and assigns (`apps/meteor/server/lib/omnichannel/RoutingManager.ts:234-336`).
- [code] The inquiry update is `updateOne({ _id, lockedAt? })`: the `lockedAt` condition is added only when the caller passes the loaded inquiry's `lockedAt`, and a zero-modified result raises `error-taking-inquiry-lockedAt-mismatch` (`packages/models/src/models/LivechatInquiry.ts:293-304`, `apps/meteor/server/lib/omnichannel/RoutingManager.ts:303-308`).
- [inference] `findNextAndLock` passes only a sort option, while `queueInquiry` in the same model explicitly asks for `returnDocument: 'after'` (`packages/models/src/models/LivechatInquiry.ts:183-185`, `packages/models/src/models/LivechatInquiry.ts:324`). The MongoDB driver's default is to return the document as it was before the update, so the inquiry handed to the worker normally has no `lockedAt` and the compare-and-set condition is probably not applied even on the worker path. This rests on the driver default and was not executed.
- [inference] The manual take through `livechat/inquiries.take` reads the status (`apps/meteor/server/lib/omnichannel/takeInquiry.ts:22-26`) and then writes without a status or version condition when the loaded inquiry has no `lockedAt`. Two agents racing on the same queued inquiry can both pass the check; both would get a subscription and the second `servedBy` write wins. The per-agent lock does not help because it protects an agent, not an inquiry.
- [code] The per-agent lock is a lease on the user document (`agentLocked`, `agentLockedAt`, 5 s timeout) and is taken only when the waiting-queue setting is on and the agent is not a bot (`packages/models/src/models/Users.ts:965-980`, `apps/meteor/server/lib/omnichannel/conditionalLockAgent.ts:12-36`).
- [code] **Queue worker.** A polling loop wakes every `Omnichannel_queue_delay_timeout` seconds (default 5), walks the active department queues one inquiry at a time, claims the next inquiry with an atomic `findOneAndUpdate` that sets `locked` / `lockedAt` (lease expires after `INQUIRY_LOCK_TIMEOUT`, default 10 s), tries to delegate it, and unlocks (`apps/meteor/server/services/omnichannel/queue.ts:34-37`, `apps/meteor/server/services/omnichannel/queue.ts:98-152`, `packages/models/src/models/LivechatInquiry.ts:29`, `packages/models/src/models/LivechatInquiry.ts:155-198`). On stop it unlocks every inquiry and resets them to queued (`apps/meteor/server/services/omnichannel/queue.ts:56-71`).
- [code] **Routing is a pluggable strategy**: `RoutingManager` holds registered methods and asks the configured one for `getNextAgent(department, ignoreAgentId)` (`apps/meteor/server/lib/omnichannel/RoutingManager.ts:81-105`). The default picks the agent with the fewest open chats (`apps/meteor/server/lib/omnichannel/routing/AutoSelection.ts:8-12`, `apps/meteor/server/lib/omnichannel/routing/AutoSelection.ts:28-51`).
- [code] The `External` strategy is the closest thing to a separate allocation service: it calls a configured URL with a shared-secret header and expects `{ username }` back; `getNextAgent` fires **ten parallel requests** and uses the first non-empty answer (`apps/meteor/server/lib/omnichannel/routing/External.ts:25-57`).
- [inference] The remaining nine answers are discarded; an external allocator that records each answer as an assignment would hold nine phantom allocations. The lesson is that an allocation call must be one idempotent command with a key, not a speculative fan-out.
- [code] Capacity limits ("max simultaneous chats") are not in the community build: the community routing code calls a hook and the working check is Enterprise (`apps/meteor/server/lib/omnichannel/routing/AutoSelection.ts:29-31`, `apps/meteor/ee/server/hooks/omnichannel/checkAgentBeforeTakeInquiry.ts:10-40` [EE-LICENCE]). The community "after take", "after queued" and "before route" steps are small default functions (a CRM webhook call or a pass-through) created with `makeFunction`, which Enterprise patches can replace at runtime (`apps/meteor/server/lib/omnichannel/hooks.ts:115-140`).
- [code] **Transfer** has three shapes. To an agent: `forwardRoomToAgent` checks the agent is online, then reuses the take path and writes the history message (`apps/meteor/server/lib/omnichannel/Helper.ts:483-578`). To a department: `forwardRoomToDepartment` either unassigns and re-queues in the target department, or delegates immediately depending on routing, queue state and department options (`apps/meteor/server/lib/omnichannel/Helper.ts:621-760`). Back to the queue: `returnRoomAsInquiry` records the history message and calls `unassignAgent`, which removes `servedBy` and the agents' subscriptions and re-queues the inquiry (`apps/meteor/server/lib/omnichannel/rooms.ts:219-267`, `apps/meteor/server/lib/omnichannel/RoutingManager.ts:175-232`). A room on hold cannot be transferred (`apps/meteor/server/lib/omnichannel/transfer.ts:66-70`). REST permissions: `view-l-room` plus `transfer-livechat-guest` for forward, `view-l-room` for return-to-queue (`apps/meteor/server/api/v1/omnichannel/room.ts:283-287`, `apps/meteor/server/api/v1/omnichannel/inquiries.ts:120-153`).
- [code] Tests: take (`apps/meteor/tests/end-to-end/api-livechat/05-inquiries.ts:133-231`), return to queue (`apps/meteor/tests/end-to-end/api-livechat/05-inquiries.ts:347-482`), forward (`apps/meteor/tests/end-to-end/api-livechat/00-rooms.ts:1299-2005`), and the queue worker with mocks (`apps/meteor/server/services/omnichannel/queue.test.ts:125-270`).
- [code] Not found: a test for two agents taking the same inquiry, or for the errors `error-inquiry-taken`, `error-taking-inquiry-lockedAt-mismatch` and `error-agent-is-locked`; searched `apps/meteor/tests/end-to-end/api-livechat/`, `apps/meteor/tests/end-to-end/api/chat.ts`, `apps/meteor/server/lib/omnichannel/*.test.ts` and `apps/meteor/server/services/omnichannel/queue.test.ts` for those names and for `concurren` and `race`.

## 7. Archive, resolve, reopen and deletion

**Omnichannel close (the nearest thing to RESOLVED).**

- [code] There is no RESOLVED or PENDING status. Closing an omnichannel room sets `closedAt`, metrics, `closer`, `closedBy`, tags and visitor status offline, and **unsets** `open` (`packages/models/src/models/LivechatRooms.ts:1635-1659`).
- [code] `closeRoom` runs one MongoDB transaction that deletes the inquiry, updates the room, and deletes all subscriptions of the room, retrying twice on transient transaction errors (`apps/meteor/server/lib/omnichannel/closeRoom.ts:29-65`, `apps/meteor/server/lib/omnichannel/closeRoom.ts:126-219`). The "room is open" check (skipped with `forceClose`) reads the room object that was loaded before the transaction, not the database row inside it (`apps/meteor/server/lib/omnichannel/closeRoom.ts:134-137`), and the room update filters only on id and type (`packages/models/src/models/LivechatRooms.ts:1638-1642`). Without `forceClose` it fails if the number of rows changed is not the expected one (`apps/meteor/server/lib/omnichannel/closeRoom.ts:183-205`).
- [inference] There is no `WHERE status is not closed` style guard on the write. What stops two concurrent closes is the inquiry delete count (exactly one delete must happen) together with MongoDB's write-conflict abort between overlapping transactions; the end-to-end test comment describes the two failure modes this produces (`apps/meteor/server/lib/omnichannel/closeRoom.ts:183-185`, `apps/meteor/tests/end-to-end/api-livechat/00-rooms.ts:3436-3437`).
- [code] After commit, outside the transaction: the closing system message, a transcript prompt, app events, the `livechat.closeRoom` callbacks (transcripts, CRM, abandonment) and notifications. A comment explains why messages stay out of the transaction: sending is large, and including part of it caused deadlocks because message hooks update the same documents (`apps/meteor/server/lib/omnichannel/closeRoom.ts:62-124`, `apps/meteor/server/lib/omnichannel/closeRoom.ts:77-79`). The callbacks run asynchronously except when `TEST_MODE` is set (`apps/meteor/server/lib/omnichannel/closeRoom.ts:106-116`).
- [code] Guards: a closing comment can be required by setting; a department can require tags before close; the visitor may close only when the setting allows it; an agent needs a subscription or the `close-others-livechat-room` permission; the route needs `close-livechat-room` (`apps/meteor/server/lib/omnichannel/closeRoom.ts:139-142`, `apps/meteor/server/lib/omnichannel/closeRoom.ts:259-275`, `apps/meteor/server/api/v1/omnichannel/room.ts:129-148`, `apps/meteor/server/api/v1/omnichannel/room.ts:210-216`, `apps/meteor/server/lib/omnichannel/closeLivechatRoom.ts:37-40`). `forceClose` is gated by an admin setting (`apps/meteor/server/api/v1/omnichannel/room.ts:221-226`).
- [code] Concurrent closes are tested: three simultaneous `closeByUser` calls on one room must produce exactly one success; the comment admits the failure message varies (`error-room-cannot-be-closed-try-again` or `Error removing inquiry`) depending on which transaction aborts (`apps/meteor/tests/end-to-end/api-livechat/00-rooms.ts:3417-3441`). Closing two different rooms in parallel succeeds (`apps/meteor/tests/end-to-end/api-livechat/00-rooms.ts:3443-3462`).
- [code] Reopen: only the email path described in Section 1 (`apps/meteor/server/lib/omnichannel/QueueManager.ts:419-478`).

**Archive (the flag).**

- [code] Ordinary rooms have an `archived` boolean on both the room and the subscriptions (`packages/core-typings/src/IRoom.ts:70`, `packages/core-typings/src/ISubscription.ts:53`). `archiveRoom` sets it on both, writes a `room-archived` system message, runs `afterRoomArchived` and notifies (`apps/meteor/server/lib/rooms/archiveRoom.ts:8-25`, `packages/models/src/models/Rooms.ts:1568-1590`).
- [code] An archived room refuses new messages with `room_is_archived`, checked before the access check (`apps/meteor/server/lib/authorization/canSendMessage.ts:27-29`); an end-to-end test covers it (`apps/meteor/tests/end-to-end/api/chat.ts:1335-1364`).
- [inference] This is an independent marker in the sense we want (a boolean that does not change any other state), but it belongs to ordinary rooms. Closing an omnichannel room never touches `archived` (`packages/models/src/models/LivechatRooms.ts:1635-1659`), so Rocket.Chat has two unrelated mechanisms where we want one status plus one marker.

**Edit.**

- [code] `executeUpdateMessage` accepts only an allowlist of changed fields, silently returns when the text is unchanged, allows the edit if the caller has `edit-message` for the room or if the `Message_AllowEditing` setting is on and the caller owns the message, and blocks edits after `Message_AllowEditing_BlockEditInMinutes` unless the caller has `bypass-time-limit-edit-and-delete` (`apps/meteor/server/meteor-methods/messages/updateMessage.ts:12`, `apps/meteor/server/meteor-methods/messages/updateMessage.ts:24-38`, `apps/meteor/server/meteor-methods/messages/updateMessage.ts:50-79`).
- [code] The write sets `editedAt` / `editedBy` and does a `$set` by `_id` with **no version or timestamp condition**, so concurrent edits are last-writer-wins; the hooks run later in `setImmediate` (`apps/meteor/server/lib/messages/updateMessage.ts:49-55`, `apps/meteor/server/lib/messages/updateMessage.ts:79-87`, `apps/meteor/server/lib/messages/updateMessage.ts:95-106`).
- [code] If `Message_KeepHistory` is on (default off), the old version is first cloned as a hidden message with a `parent` pointer in the same collection (`apps/meteor/server/lib/messages/updateMessage.ts:44-47`, `packages/models/src/models/Messages.ts:1103-1116`, `apps/meteor/server/settings/message.ts:160`). The REST wrapper is `chat.update` (`apps/meteor/server/api/v1/chat.ts:323-391`). Tests: update success, unchanged text, custom fields (`apps/meteor/tests/end-to-end/api/chat.ts:2267-2282`, `apps/meteor/tests/end-to-end/api/chat.ts:2363-2417`).

**Delete.**

- [code] `deleteMessage` has three modes selected by two settings that both default to off: (a) default **hard delete** by `removeById`; (b) with `Message_ShowDeletedStatus`, a **tombstone** that blanks the text, attachments, urls, mentions and reactions and sets `t: 'rm'` while keeping the row; (c) with `Message_KeepHistory`, a hidden copy or a hidden flag. A message that is a thread parent always takes the keep-history and tombstone path (`apps/meteor/server/lib/messages/deleteMessage.ts:30-82`, `packages/models/src/models/Messages.ts:1128-1141`, `packages/models/src/models/Messages.ts:1158-1182`, `apps/meteor/server/settings/message.ts:144-147`).
- [code] A hard delete is not really gone: the base model copies the document into a shared trash collection with `_deletedAt` before removing it, for models constructed with the trash collection, which includes messages (`packages/models/src/models/BaseRaw.ts:321-352`, `apps/meteor/server/models.ts:129`). The delta sync reads deletions from that collection (`apps/meteor/server/publications/messages.ts:109-125`). The trash collection is purged by a TTL index: entries expire 30 days after `_deletedAt` (`packages/models/src/models/Trash.ts:18`; the collection is built in `apps/meteor/server/database/trash.ts:5` and the model creates its indexes in its constructor, `packages/models/src/models/BaseRaw.ts:92`).
- [code] The permission check is a function of the deleting user and the message: `force-delete-message` always allows; otherwise the `Message_AllowDeleting` setting must be on and the user needs `delete-message`, or `delete-own-message` for their own message; a time window applies unless `bypass-time-limit-edit-and-delete`; read-only rooms add a rule (`apps/meteor/server/lib/authorization/canDeleteMessage.ts:13-77`). The REST route is `chat.delete`, which can delete by message id or by file id and can act "as user" with `force-delete-message` (`apps/meteor/server/api/v1/chat.ts:604-666`).
- [code] The delete itself is a series of separate writes with no transaction: thread counters, the room's last message or message count, read receipts, files, `afterDeleteMessage` callbacks, then the notifications (`apps/meteor/server/lib/messages/deleteMessage.ts:30-106`). Tests include delete by id, by file id, thread messages and read-only rooms (`apps/meteor/tests/end-to-end/api/chat.ts:2452-2838`).
- [code] Removing a closed omnichannel room deletes its messages, receipts, subscriptions, inquiry, room and receipt archive with `Promise.allSettled` over the six removals and throws if any failed; there is no transaction, so a partial removal is possible (`apps/meteor/server/lib/omnichannel/rooms.ts:269-313`). It needs the room to be closed and the permission `remove-closed-livechat-room` (`apps/meteor/server/api/v1/omnichannel/room.ts:479-507`); a bulk variant removes all closed rooms (`apps/meteor/server/api/v1/omnichannel/room.ts:508-532`).

## 8. Realtime event contracts

- [code] The write path ends with fire-and-forget notifications: `void api.broadcast('watch.messages', { message })` after a message changes, `watch.subscriptions` for subscription changes, `watch.inquiries` with `{ clientAction, inquiry, diff }` for queue changes (`apps/meteor/server/lib/notifyListener.ts:493-503`, `apps/meteor/server/lib/notifyListener.ts:218-228`). The `void` means the caller neither waits for nor retries a failed broadcast.
- [code] First hop of a normal user message: `sendMessage` awaits `afterSaveMessage`, which ends with `void Message.afterSave(...)`; `afterSave` first awaits the URL / OEmbed parse and only then calls `void notifyOnMessageChange(...)`, and a comment says the notification is deliberately deferred until after the acknowledgement to the UI and these hooks (`apps/meteor/server/hooks/messages/afterSaveMessage.ts:34`, `apps/meteor/server/services/messages/service.ts:289-295`). The notification at the end of `sendMessage` itself is the room-changed one, not the message event (`apps/meteor/server/lib/messages/sendMessage.ts:293-295`).
- [inference] The new-message event is therefore detached twice (a `void` inside a `void`) and is sent after the URL parse, normally after the sender's request has already returned. A failure or a crash in that detached chain loses the event with no retry, and its timing depends on how long the parse takes.
- [code] The events form a single typed catalogue: `watch.messages`, `watch.subscriptions`, `watch.inquiries`, `notify.deleteMessage`, `notify.messagesRead`, `omnichannel.room`, `user.activity` and many more, each with a typed payload (`packages/core-services/src/events/Events.ts:91`, `packages/core-services/src/events/Events.ts:115`, `packages/core-services/src/events/Events.ts:147`, `packages/core-services/src/events/Events.ts:168`, `packages/core-services/src/events/Events.ts:246`, `packages/core-services/src/events/Events.ts:287`).
- [code] The message event payload is the **whole message object** (`packages/core-services/src/events/Events.ts:168`). The streamer emits it on the per-room stream `room-messages`, keyed by room id, and on an aggregate `__my_messages__` event that is filtered per subscriber (`packages/streamer/src/listeners.module.ts:256-269`, `packages/streamer/src/notifications.module.ts:148-177`). A hard delete uses a different, smaller event carrying only `{ _id }` (`apps/meteor/server/lib/messages/deleteMessage.ts:81`, `packages/streamer/src/listeners.module.ts:478-480`); a tombstone delete re-emits the whole (blanked) message instead (`apps/meteor/server/lib/messages/deleteMessage.ts:97-101`).
- [inference] Not found: any event id, version or sequence in these payloads (the signatures at `packages/core-services/src/events/Events.ts:168` and `packages/core-services/src/events/Events.ts:246` carry only the entity and a client action), so a consumer cannot order or de-duplicate events and must treat each as "replace the object".
- [code] Inquiry updates are fanned out to channels by audience: the inquiry id, `agent/<id>` for a default agent, `department/<id>`, and `public` when neither applies; pure lock-metadata updates are suppressed after the first channel (`packages/streamer/src/listeners.module.ts:297-343`). Agent changes use `omnichannel.room` with `{ type: 'agentData' }` (`apps/meteor/server/lib/omnichannel/Helper.ts:398-405`, `packages/streamer/src/listeners.module.ts:507-509`).
- [code] Subscribe-time authorisation: clients cannot write to the message stream, and read access is decided per room by `canReadRoom`; when a subscription is removed the server drops that user's stream subscription (`packages/streamer/src/notifications.module.ts:86-109`, `packages/streamer/src/notifications.module.ts:137-146`, `packages/streamer/src/listeners.module.ts:280-283`).
- [code] Typing is an ephemeral event, never stored: `user.activity` becomes a `user-activity` room notification (`packages/streamer/src/listeners.module.ts:252-254`). An error on send is returned to the sender as an ephemeral message event (`apps/meteor/server/meteor-methods/messages/sendMessage.ts:107-114`).
- [doc] An accepted decision record says every cross-process delivery is a service-broker event, with stream fan-out carried by the broker event `stream` and an `origin` field used to avoid echo (`docs/adr/0005-stream-fan-out-rides-the-service-broker.md:9-14`). The same record lists defects that came from per-deployment wiring, for example events that never reached clients in one deployment mode (`docs/adr/0005-stream-fan-out-rides-the-service-broker.md:40-51`).
- [code] The only after-commit mechanism I found is in-process: callbacks registered on the Mongo session run once the transaction commits, in memory (`apps/meteor/server/database/utils.ts:29-47`). Nothing is persisted, so a crash between commit and callback loses the notification.
- [code] Not found: an end-to-end test of stream delivery; searched `apps/meteor/tests/end-to-end/` and `apps/meteor/tests/e2e/` for `stream-room-messages` and `room-messages`. Unit tests stub `notifyOnMessageChange`.

## 9. Reconnect, recovery and duplicates

- [code] The web client recovers after a dropped connection with `useLoadMissedMessages`: when the connection returns, for each opened room it calls `chat.syncMessages` with `lastUpdate` = the timestamp of the newest loaded message and `fromTs` = the oldest loaded one, then upserts the returned messages and removes the returned deletions (`apps/meteor/client/views/root/hooks/useLoadMissedMessages.ts:23-61`, `apps/meteor/client/views/root/hooks/useLoadMissedMessages.ts:66-81`). A comment states the trade-off: edits to messages older than `fromTs` are not reported because those messages are not loaded (`apps/meteor/client/views/root/hooks/useLoadMissedMessages.ts:12-22`).
- [code] The set of deletions that sync can report is bounded: it comes from the trash collection, whose entries expire 30 days after the delete (`packages/models/src/models/Trash.ts:18`, `apps/meteor/server/publications/messages.ts:109-125`).
- [code] The server side is `getMessageHistory`: with `lastUpdate` it returns messages whose `_updatedAt` is later plus trash entries whose `_deletedAt` is later; with `type` and `next` / `previous` it pages through those two sets by cursor; `fromTs` is only honoured with `lastUpdate` (`apps/meteor/server/publications/messages.ts:109-125`, `apps/meteor/server/publications/messages.ts:167-253`). The route validates parameter combinations (`apps/meteor/server/api/v1/chat.ts:674-768`).
- [inference] Recovery compares wall-clock timestamps (the client sends a message's creation `ts` and the server compares it with `_updatedAt`), not sequence numbers, so there is no gap detection and a message written with an older `ts` than the client's newest could be missed. Hard-deleted messages are found only while their trash rows exist, and those expire after 30 days (`packages/models/src/models/Trash.ts:18`), so a client that stays offline longer than that can never learn of a hard delete through this sync and keeps showing the message. This is workable for a chat room but is the weakness a per-conversation `sequence` and `after_sequence` fetch removes.
- [code] There is also a plain "deleted since" route for clients that only need deletions (`apps/meteor/server/api/v1/chat.ts:1016-1057`).
- [code] Duplicate delivery is not addressed in the contract: events carry no id (Section 8), and the client reconciles by message `_id`, upserting messages and deleting by id (`apps/meteor/client/views/root/hooks/useLoadMissedMessages.ts:42-49`).
- [code] Tests: end-to-end for `chat.syncMessages` including `lastUpdate`, `fromTs`, cursor types and parameter conflicts (`apps/meteor/tests/end-to-end/api/chat.ts:3932-4330`), and a unit spec for the client hook (`apps/meteor/client/views/root/hooks/useLoadMissedMessages.spec.ts:82-124`).

## 10. Tenant boundaries

- [code] Not found: any tenant concept. `grep -rli tenant --include=*.ts` over `apps/meteor/server`, `packages/core-typings/src` and `packages/models/src` returned no file. Rocket.Chat is one workspace per deployment.
- [code] The nearest scoping is the **department** (`departmentId` on rooms and inquiries). In the community build the function that restricts department queries is a no-op; the Enterprise patch applies unit / monitor restrictions when the licence module is present (`packages/omni-core/src/hooks/applyDepartmentRestrictions.ts:5-7`, `ee/packages/omni-core-ee/src/patches/applyDepartmentRestrictions.ts:9-24` [EE-LICENCE]).
- [code] Restrictions are injected by callback into queries at call sites (`livechat.applyRoomRestrictions`), for example in bulk close and bulk remove (`apps/meteor/server/lib/omnichannel/closeOmnichannelConversations.ts:19-24`, `apps/meteor/server/api/v1/omnichannel/room.ts:523-528`).
- [inference] Isolation here is a convention each call site must remember, with no database-level enforcement. It cannot be a model for tenant isolation.
- [code] Customer identity is a bearer token. The visitor model indexes `token` without a uniqueness constraint, and the visitor endpoints trust `token` plus a room check (`packages/models/src/models/LivechatVisitors.ts:29-31`, `apps/meteor/server/api/v1/omnichannel/message.ts:29-38`, `apps/meteor/server/lib/omnichannel/rooms.ts:77-80`).
- [code] Stream names are room ids, inquiry ids, `agent/<id>`, `department/<id>` and `public`, with no tenant prefix (`packages/streamer/src/listeners.module.ts:310-342`).
- [doc] One positive pattern: the project rule that code outside a model never passes filters or updates to generic collection methods, only named model methods, which keeps a query next to its index and would be the natural place for a mandatory tenant predicate (`docs/database-access.md:3-6`, `docs/database-access.md:18-26`).

## 11. Attachments

- [code] A message holds structured `attachments` (link cards, images, audio, video) and uploaded `files`; the older single `file` field is deprecated (`packages/core-typings/src/IMessage/IMessage.ts:194-202`). Attachment URL fields go through the same absolute-URL and `javascript:` checks as message links (`apps/meteor/server/lib/messages/sendMessage.ts:77-150`). End-to-end tests post malicious values in each attachment field and expect rejection (`apps/meteor/tests/end-to-end/api/chat.ts:116-440`).
- [code] Upload validation (`validateFileUpload`) requires an existing room the uploader can access, the global upload switch, a direct-message switch, a maximum size where `-1` means unlimited, a content-type allow / deny check, an encryption check and an apps-engine pre-upload event (`apps/meteor/server/lib/media/file-upload/lib/FileUpload.ts:126-193`).
- [code] Download access requires an authenticated user and then two optional restrictions, "room members only" (default on) and "anyone who can access the room" (default off) (`apps/meteor/server/lib/media/file-upload/lib/FileUpload.ts:525-555`, `apps/meteor/server/settings/file-upload.ts:35`, `apps/meteor/server/settings/file-upload.ts:49`). Storage keys are built from the room id and user id (`apps/meteor/server/lib/media/file-upload/lib/FileUpload.ts:68`).
- [code] The visitor upload route authenticates with an `x-visitor-token` header, requires the visitor's open room and the livechat upload setting, and falls back to a 100 MiB size limit when the global limit is unset (`apps/meteor/server/api/v1/omnichannel/upload.ts:10-53`). End-to-end tests cover it (`apps/meteor/tests/end-to-end/api-livechat/00-rooms.ts:2209-2371`).
- [code] Deleting a message either removes its uploaded files or marks them `_hidden`, depending on the keep-history setting (`apps/meteor/server/lib/messages/deleteMessage.ts:53-76`). Retention pruning deletes files first, in batches (`apps/meteor/server/lib/rooms/cleanRoomHistory.ts:56-105`).
- [inference] Attachments are part of the message document and are authorised through the room, so they inherit whatever room-level authorisation exists; there is no separate attachment entity with its own tenant or lifecycle. This is a poor fit for a relational model where the attachment is a row with an owner and a state.

## 12. Authorization and audit

- [code] Authorisation is role-based permissions checked per action with the room id as the scope, for example `hasPermissionAsync(uid, 'edit-message', rid)` (`apps/meteor/server/meteor-methods/messages/updateMessage.ts:50`, `apps/meteor/server/lib/authorization/canDeleteMessage.ts:36-58`). Room access is a **chain of validators, first true wins**: public rooms inside teams, public rooms, membership with a view permission, access to a discussion's parent room, and finally the livechat validators (`packages/authorization/src/canAccessRoom.ts:24-106`, `packages/authorization/src/canAccessRoom.ts:112-139`).
- [code] The livechat validators grant access to holders of `view-livechat-rooms`, to the serving agent (and, for closed rooms, to holders of `view-livechat-room-closed-by-another-agent`), to a visitor presenting the room's token for an open room, to agents who can preview a queued inquiry when the routing method allows previews, to department agents holding `view-livechat-room-closed-same-department` for closed rooms, and, hard-coded, to the built-in user `rocket.cat` for every livechat room (`apps/meteor/server/lib/omnichannel/roomAccessValidator.compatibility.ts:14-96`).
- [code] Sending is gated by `validateRoomMessagePermissionsAsync`: archived, access, blocked subscription, read-only without `post-readonly`, muted (`apps/meteor/server/lib/authorization/canSendMessage.ts:18-55`). REST routes declare required permissions inline, for example `view-l-room` for take and return-to-queue (`apps/meteor/server/api/v1/omnichannel/inquiries.ts:65-66`, `apps/meteor/server/api/v1/omnichannel/inquiries.ts:129-130`).
- [code] The take route accepts an optional `userId` in the body and only checks that the user exists, so a caller with `view-l-room` can take an inquiry on behalf of another agent (`apps/meteor/server/api/v1/omnichannel/inquiries.ts:64-77`). The end-to-end test relies on this to take as a freshly created agent (`apps/meteor/tests/end-to-end/api-livechat/05-inquiries.ts:186-207`).
- [code] The visitor-facing routes carry no session at all: they are declared without `authRequired` and trust the `token` in the body or query (`apps/meteor/server/api/v1/omnichannel/message.ts:24-27`, `apps/meteor/server/api/v1/omnichannel/room.ts:129-131`).
- [code] Audit in the community build is thin: audit server events exist for user changes and setting updates (`apps/meteor/server/settings/lib/auditedSettingUpdates.ts:47`, `apps/meteor/server/lib/auditServerEvents/userChanged.ts:166`) and the event type enum lists only failed login and login (`packages/core-typings/src/IServerEvent.ts:15-18`). The message audit API and the audit-log model are Enterprise (`apps/meteor/ee/server/api/audit.ts:21` [EE-LICENCE], `apps/meteor/ee/server/models/AuditLog.ts:1` [EE-LICENCE]).
- [inference] For conversation transitions and messages the community trail is only what the domain happens to write: the transfer history system message, the `editedAt` / `editedBy` fields, `closer` / `closedBy` on the room, and optional hidden edit copies. There is no append-only record of "who changed status from what to what".

## 13. Transaction boundaries and concurrency

- [code] Sending a message is **not transactional**. `sendMessage` inserts the message, then runs the hooks, which separately update the room's counters and last message, the subscriptions' unread counters, thread data and notification queues. The room-changed notification closes `sendMessage`; the new-message event is sent later from a detached task (Section 8) (`apps/meteor/server/lib/messages/sendMessage.ts:283-295`, `apps/meteor/server/hooks/messages/afterSaveMessage.ts:21-34`, `apps/meteor/server/hooks/messages/notifyUsersOnMessage.ts:197-201`, `apps/meteor/server/services/messages/service.ts:289-295`).
- [code] Where transactions exist they are few and deliberate. A search for `startTransaction` and `withTransaction` over `apps/meteor/server` and `apps/meteor/ee/server` finds a generic helper (used when saving a user), the OAuth login, room-plus-inquiry creation, room close, and an Enterprise contact-verification patch (`apps/meteor/server/database/utils.ts:65-90`, `apps/meteor/server/lib/users/saveUser/saveUser.ts:347`, `apps/meteor/server/lib/auth-providers/custom-oauth/customOAuth.ts:311`, `apps/meteor/server/lib/omnichannel/QueueManager.ts:260`, `apps/meteor/server/lib/omnichannel/closeRoom.ts:36`, `apps/meteor/ee/server/patches/verifyContactChannel.ts:29` [EE-LICENCE]). The same search, extended with `startSession`, over the message libraries, the message service, the message hooks and the message Meteor-method folder returned nothing.
- [doc] The data-access guide says a model write method that takes no options cannot take part in a transaction, and to add a session parameter when a caller needs one (`docs/database-access.md:33-34`), which confirms that transactions are opt-in per call, not the default.
- [code] Transient transaction errors are retried by label (`UnknownTransactionCommitResult`, `TransientTransactionError`) (`apps/meteor/server/database/utils.ts:22-24`).
- [code] The chained hook runner has no error handling: hooks are piped one after another, so the first one that throws stops the rest and the rejection reaches the caller, while the writes of earlier hooks stay applied. The fire-and-forget runner schedules each callback with a zero-delay timer and ignores its result (`apps/meteor/server/lib/callbacks/callbacksBase.ts:62-85`, `apps/meteor/server/lib/callbacks/callbacksBase.ts:87-101`).
- [inference] Because the message insert and its derived state (room counters, unread counters, last message) are separate writes, a crash or an exception between them leaves the derived state wrong until something recomputes it. `afterSaveMessage` is awaited in `sendMessage`, so a hook failure surfaces as an error to the caller after the message is already stored.
- [code] Concurrency control is a mix of: atomic single-document claims (`findNextAndLock`, `acquireAgentLock`, and the optionally `lockedAt`-conditional take) with time-based lease expiry (`packages/models/src/models/LivechatInquiry.ts:155-187`, `packages/models/src/models/Users.ts:965-980`); unique indexes (subscription per room and user, one open livechat room per visitor token) (`packages/models/src/models/Subscriptions.ts:38`, `packages/models/src/models/LivechatRooms.ts:77-85`); transaction aborts for close; and `$inc` for counters (`packages/models/src/models/Rooms.ts:890-896`).
- [code] Not found: optimistic version fields on messages, rooms, subscriptions or inquiries. Searching `IMessage`, `IRoom`, `IInquiry` and `ISubscription` under `packages/core-typings/src` for `version`, `etag` and `revision` finds only federation event versions and an avatar ETag. Message edits are last-writer-wins (`apps/meteor/server/lib/messages/updateMessage.ts:79-87`).
- [code] Read-then-write sites in the omnichannel flow that are not protected by a condition: the pre-check in `takeInquiry` (`apps/meteor/server/lib/omnichannel/takeInquiry.ts:22-26`), the "does a subscription exist" check in `createLivechatSubscription` (protected only by the unique index) (`apps/meteor/server/lib/omnichannel/Helper.ts:288-291`), and `sendMessage`'s existence check (Section 3).

## 14. Background jobs and retention

- [code] The omnichannel queue worker is a polling loop inside the application process, started only when the configured routing method auto-assigns (`apps/meteor/server/services/omnichannel/queue.ts:168-182`), with a reconciliation step and per-queue tracing (`apps/meteor/server/services/omnichannel/queue.ts:98-107`, `apps/meteor/server/services/omnichannel/queue.ts:184-226`). It tracks time-in-queue metrics (`apps/meteor/server/services/omnichannel/queue.ts:272-275`).
- [code] Scheduled omnichannel behaviours are Enterprise and use a MongoDB-backed job scheduler (Agenda): auto-transfer of an unanswered chat to another agent or back to the queue after a timeout, close of a chat that sat queued too long, and auto-close of on-hold chats. They act as the built-in system user `rocket.cat` (`apps/meteor/ee/server/lib/omnichannel/AutoTransferChatScheduler.ts:34-44` [EE-LICENCE], `apps/meteor/ee/server/lib/omnichannel/AutoTransferChatScheduler.ts:46-56` [EE-LICENCE], `apps/meteor/ee/server/lib/omnichannel/AutoTransferChatScheduler.ts:79-125` [EE-LICENCE], `apps/meteor/ee/server/lib/omnichannel/QueueInactivityMonitor.ts:77-87` [EE-LICENCE], `apps/meteor/ee/server/lib/omnichannel/QueueInactivityMonitor.ts:102-125` [EE-LICENCE], `apps/meteor/ee/server/lib/omnichannel/AutoCloseOnHoldScheduler.ts:85` [EE-LICENCE]). In the community build, deactivating an agent bulk-closes their rooms through `closeRoom`, one call per room (`apps/meteor/server/lib/omnichannel/closeOmnichannelConversations.ts:14-34`).
- [code] Message retention is a cron job that, per room type (channels, groups, DMs) with a global maximum age and optional per-room overrides, calls `cleanRoomHistory`; options protect pinned messages, discussions and threads, and a "files only" mode removes just attachments (`apps/meteor/server/lib/rooms/retention/cronPruneMessages.ts:12-23`, `apps/meteor/server/lib/rooms/retention/cronPruneMessages.ts:31-91`, `apps/meteor/server/lib/rooms/cleanRoomHistory.ts:28-105`). The schedule is re-deployed when the settings change (`apps/meteor/server/lib/rooms/retention/cronPruneMessages.ts:93-120`).
- [inference] The global retention types are channels, groups and DMs only (`apps/meteor/server/lib/rooms/retention/cronPruneMessages.ts:12`); omnichannel rooms are not among them, so closed conversations are never pruned by this job. They leave only through the manual removal endpoints (Section 7).
- [code] Expiry mechanisms found: a one-day TTL on the email message history (`packages/models/src/models/EmailMessageHistory.ts:12-14`); a 30-day TTL on the shared trash collection that holds hard-deleted documents, which also bounds how long delta sync can report a deleted message (`packages/models/src/models/Trash.ts:18`); and a TTL index on a message `expireAt` field (`packages/models/src/models/Messages.ts:49`). The only writer of `expireAt` that I found is the page-navigation tracker, which sets it to one month ahead on navigation-history system messages saved without a room id; the extra data is merged into the stored message (`apps/meteor/server/lib/omnichannel/tracking.ts:41-46`, `apps/meteor/server/lib/omnichannel/tracking.ts:53`, `packages/models/src/models/Messages.ts:1397`).
- [code] Not found: a durable job queue in the community build. The queue worker and cron are in-process timers; Enterprise jobs use a database-backed scheduler.

## 17. Meteor / MongoDB-specific architecture not to copy

- [code] **Meteor runtime and DDP streams.** The server is a Meteor 3 application and clients subscribe to named streams that mimic a client-side Mongo cache (`apps/meteor/.meteor/release:1`, `packages/streamer/src/listeners.module.ts:297-298`). Nothing in our PostgreSQL / Centrifugo design corresponds to this.
- [code] **Denormalised embedded copies.** Sender (`u`), visitor (`v`), room `lastMessage`, inquiry `lastMessage`, room `servedBy` and per-subscription counters are copies kept in step by hooks (`packages/core-typings/src/IRoom.ts:38`, `packages/core-typings/src/IInquiry.ts:35-44`, `apps/meteor/server/hooks/omnichannel/saveLastMessageToInquiry.ts:9-34`). The queue reconciler and the last-message refresh on delete are code that repairs or recomputes such copies (`apps/meteor/server/services/omnichannel/queue.ts:184-226`, `apps/meteor/server/lib/messages/deleteMessage.ts:84-91`).
- [inference] Those two pieces of code exist because copies kept by hooks can diverge from their source; the reconciler's own comments call its cases precautions (`apps/meteor/server/services/omnichannel/queue.ts:236-237`, `apps/meteor/server/services/omnichannel/queue.ts:249`), so I cannot say how often the divergence happens in practice.
- [code] **Timestamps as the change log.** `_updatedAt` on every write and a shared trash collection with `_deletedAt` let clients ask "what changed since T", but the trash entries expire after 30 days (`packages/models/src/models/Trash.ts:18`, `packages/models/src/models/setUpdatedAt.ts:1-20`, `packages/models/src/models/BaseRaw.ts:321-352`, `apps/meteor/server/publications/messages.ts:109-125`).
- [code] **Counters with `$inc` and flags with sparse / partial indexes**, including a marker field `_enforceSingleRoom` that exists only so a unique index can be created over legacy data (`packages/models/src/models/Subscriptions.ts:519-540`, `apps/meteor/server/lib/omnichannel/Helper.ts:147-149`).
- [code] **Mongo multi-document transactions** used sparingly, with error-label retries (`apps/meteor/server/database/utils.ts:22-24`, `apps/meteor/server/lib/omnichannel/closeRoom.ts:29-65`).
- [code] **Runtime settings as control flow.** Domain code reads settings inline; for example the first inquiry status depends on three settings and the routing configuration (`apps/meteor/server/lib/omnichannel/QueueManager.ts:130-167`), and delete behaviour on two (`apps/meteor/server/lib/messages/deleteMessage.ts:33-34`). Behaviour is a matrix of configuration, not of code.
- [code] **Licence-gated runtime patching** (`makeFunction`, `License.hasModule`), which puts a licence check between a call and its implementation (`ee/packages/omni-core-ee/src/patches/applyDepartmentRestrictions.ts:16-18` [EE-LICENCE]).
- [doc] **Service broker** between in-process "services" and the streamer, with a Moleculer-based transport for multi-instance deployments (`docs/adr/0005-stream-fan-out-rides-the-service-broker.md:15-17`). The same decision record lists defects of the earlier per-deployment wiring that its decision (one broker channel for every cross-process delivery) is meant to remove, so those defects describe the old design, not necessarily the current code (`docs/adr/0005-stream-fan-out-rides-the-service-broker.md:40-51`).
- [code] **Unordered multi-collection deletes** with `Promise.allSettled` instead of one transaction (`apps/meteor/server/lib/omnichannel/rooms.ts:287-298`).
- [code] **Time-based cursors** on a mutable millisecond field (`apps/meteor/server/lib/messages/loadRoomHistory.ts:25-27`).
- [inference] None of these is worth porting. The useful ideas (a named-query model layer, typed event catalogue, claim-and-lease queue, department-scoped audiences) can be re-expressed without them.
