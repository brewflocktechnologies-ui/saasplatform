## 1. Conversation identity and lifecycle

- [code] Zulip has no conversation table. A message points at a `Recipient` (an audience: a stream or a direct-message group) and, for stream messages, carries its topic as a plain string column (`zerver/models/messages.py:31`, `zerver/models/messages.py:84`). `Recipient` is a (type, type_id) pair, unique together (`zerver/models/recipients.py:38-49`); for a direct-message group the type id points at an object whose membership is the fixed set of users (`zerver/models/recipients.py:23-32`, `zerver/models/streams.py:369-371`).
- [code] A topic is therefore not an entity. It exists only as the `subject` value on messages, and direct messages store a placeholder character instead of a topic so that the query planner does not mis-estimate (`zerver/models/messages.py:61-74`).
- [code] Ids are database auto-increment integers, shared by all realms: `Message.id` is an `AutoField` and `UserMessage.id` a `BigAutoField` (`zerver/models/messages.py:26`, `zerver/models/messages.py:457`).
- [code] The only lifecycle transitions that exist are on the channel and on message text: a channel can be deactivated ("archived") and reactivated (Section 7), and a topic is "resolved" by renaming it with a check-mark text prefix (`zerver/lib/topic.py:34`, `zerver/lib/message.py:283-305`). There is no status column on a conversation, no open or pending state and no owner.
- [inference] This is the clearest "do not copy" for the matrix. We need a conversation row with an explicit status enum, because sequencing, assignment and resolution all hang off it; Zulip's missing conversation row is also why it can only order by a global message id (Section 4).

## 2. Message schema and sender identity

- [code] A message row holds the sender (foreign key to a user), the recipient, the realm, a type flag (normal or a resolve-topic notification), the subject, raw content, rendered HTML and its version, the send time, the sending client, the last edit time, an edit-history JSON text and several `has_*` booleans (`zerver/models/messages.py:25-116`).
- [code] Sender identity is a reference to a user row, not an embedded copy; bot accounts are user rows with an `is_bot` flag, and the message row records which client program sent it (`zerver/models/messages.py:27`, `zerver/models/messages.py:99-100`, `zerver/models/users.py:556`). Event payloads, by contrast, carry denormalised sender fields (name, email, avatar) built at delivery time (`zerver/lib/event_types.py:176-194`).
- [code] The send time is the application server's clock; only "forged" sends by privileged mirror clients may supply a timestamp (`zerver/actions/message_send.py:2006-2010`).
- [code] Rendering of Markdown to HTML happens before the database transaction and travels in the send request (`zerver/lib/message.py:125-128`). [doc] The docs put all input validation and rendering in `check_message`, ahead of the atomic `do_send_messages` (`docs/subsystems/sending-messages.md:73-81`).
- [code] A system-style message is the same table with a different `type` value (`zerver/models/messages.py:40-59`). [inference] There is no separate sender kind for a customer, because Zulip has no customer concept (Section 6).

## 4. Ordering and pagination

- [code] The ordering key is the message id. Fetch queries bound and order by it, the rows are sorted by id in Python, and the web client sorts incoming message events by id before inserting them (`zerver/lib/narrow.py:1293-1304`, `zerver/lib/narrow.py:1579-1582`, `web/src/server_events.js:102-106`).
- [code] Paging is by anchor: `anchor` is a message id or one of `oldest`, `newest`, `first_unread` or `date`, with `num_before`, `num_after` and `include_anchor`; at most 5000 messages per call (`zerver/lib/narrow.py:1179-1235`, `zerver/views/message_fetch.py:35`, `zerver/views/message_fetch.py:103-122`, `zerver/views/message_fetch.py:148-159`).
- [code] The range query is at most two queries, ids at or below the anchor descending with a limit and ids at or above it ascending with a limit, joined with `union all`; a headroom row is fetched and trimmed afterwards (`zerver/lib/narrow.py:1256-1321`, `zerver/lib/narrow.py:1345-1354`).
- [code] The response says whether the client now has the complete range: `found_anchor`, `found_oldest`, `found_newest`, `history_limited` and the resolved `anchor` (`zerver/lib/narrow.py:1386-1410`, `zerver/views/message_fetch.py:317-327`). A test pins these flags on a table of cases (`zerver/tests/test_message_fetch.py:1507-1560`). A source comment names a known bug in `history_limited` for one-sided queries after the anchor is bumped (`zerver/lib/narrow.py:1391-1402`).
- [code] A realm-wide cut-off, `first_visible_message_id`, clips every fetch (`zerver/lib/narrow.py:1353-1358`, `zerver/lib/narrow.py:1497`).
- [code] The multi-query fetch runs in a read-only repeatable-read transaction so the page is consistent with itself and with deletions in between (`zerver/views/message_fetch.py:209-232`).
- [inference] Ordering by a global database sequence is not commit order: the id is allocated when the row is inserted inside the sending transaction (`zerver/actions/message_send.py:1042-1063`), so a transaction holding a lower id can commit after one holding a higher id. Zulip copes because events are published after commit and clients sort and insert by id (`web/src/message_list_data.ts:317-335`), and because the client refetches when it notices it missed a newer id (Section 9). I did not run this scenario. For us, a per-conversation `sequence` assigned under a conversation lock removes the problem.
- [code] There is no opaque page token; continuity rests on the client remembering the last id it holds (`zerver/views/message_fetch.py:138-139`, `zerver/views/message_fetch.py:158-159`).

## 5. Read / unread

- [code] Read state is per (user, message): a `UserMessage` row with a bit field containing `read`, `starred`, `mentioned` and others, unique on (user, message) (`zerver/models/messages.py:456-520`). The rows for all recipients are created inside the send transaction (`zerver/actions/message_send.py:1098-1134`).
- [doc] Counting unread would need unbounded history, so the initial state carries the ids of unread messages grouped by conversation key; three event types keep it current (`docs/subsystems/unread_messages.md:3-13`, `docs/subsystems/unread_messages.md:48-52`).
- [code] "Mark everything read" updates flags in locked batches of 2000, each in its own transaction, and sends one event after the last batch, using the unsafe publisher (`zerver/actions/message_flags.py:45-94`). A targeted update locks the user's rows, skips messages that already have the flag, creates "historical" rows for messages the user never received, applies a bit-or or bit-and and emits one event on commit (`zerver/actions/message_flags.py:346-363`, `zerver/actions/message_flags.py:380-427`). Marking unread ignores messages in channels the user is not subscribed to (`zerver/actions/message_flags.py:315-344`).
- [code] The server-side state used at register time keeps unread ids in dictionaries and applies message, flag and delete events with set and pop operations (`zerver/lib/events.py:1031-1038`, `zerver/lib/events.py:1798-1807`, `zerver/lib/events.py:1837-1851`, `zerver/lib/message.py:1233`, `zerver/lib/message.py:1280-1287`). [inference] Those operations tolerate repeats.
- [inference] Per-recipient rows give exact per-message read state but cost one row per recipient per message and a bulk update for "mark all read". Our per-participant read cursor is O(1) per message and per read action, at the price of no per-message flags.

## 7. Archive, resolve, reopen and deletion

- [code] Channel archive sets a `deactivated` flag, writes an audit row, sends an `is_archived` update event on commit and posts a system notice, all in one transaction (`zerver/actions/streams.py:128-204`). Unarchive reverses it, also with an audit row and an event (`zerver/actions/streams.py:232-308`). Both refuse a no-op transition by raising (`zerver/actions/streams.py:130-132`, `zerver/actions/streams.py:239-240`); neither function takes a row lock, and the check reads the object passed in.
- [code] While a channel is archived, modifying its messages is refused (`zerver/lib/message.py:612-614`). Clients that cannot process archived channels receive create and delete events in place of the `is_archived` update (`zerver/tornado/event_queue.py:274-282`).
- [code] Resolve and reopen of a topic are renames that add or remove a prefix, with a notification message of a dedicated type (`zerver/lib/message.py:283-305`, `zerver/models/messages.py:40-42`).
- [code] Deletion never destroys a live row first. Rows are copied to archive tables under an archive-transaction record, related rows (flags, reactions, attachments) in the same transaction, and then deleted, in chunks (`zerver/lib/retention.py:10-23`, `zerver/lib/retention.py:136-194`). A user-initiated delete uses the same path (`zerver/actions/message_delete.py:49-58`). The delete event is grouped per recipient and topic and sent on commit (`zerver/lib/retention.py:335-413`). Archived data is vacuumed after 30 days (`zproject/default_settings.py:652`), and a restore function exists (`zerver/lib/retention.py:664-679`).
- [inference] Strong precedent for soft delete plus a tombstone event sent in the same transaction. The archive-then-delete structure is heavier than we need: we can flag rows deleted and purge later.

## 8. Realtime event contracts

- [code] **Single funnel for publication.** `send_event_on_commit(realm, event, users)` normalises the event to a plain dict, in test mode round-trips it through JSON to catch non-serialisable data early, and registers a database `on_commit` callback that calls `send_event_rollback_unsafe` (`zerver/tornado/django_api.py:275-292`). The unsafe variant maps the realm to one or more Tornado shards and publishes `{event, users}` to a RabbitMQ queue named for the shard (`zerver/tornado/django_api.py:250-272`, `zerver/tornado/sharding.py:49-52`).
- [code] A comment states the convention: prefer the on-commit variant; call it only from `zerver/actions/*.py`; every call site must be covered by a test in `test_events.py` with a schema in `event_schema.py` (`zerver/tornado/django_api.py:203-216`). Observed: 143 non-test call sites of `send_event_on_commit(` in 44 files, 9 of them outside `zerver/actions/` (8 in `zerver/lib/`, 1 in `zerver/views/`), [inference] so the "only from actions" convention is not strictly held (command in Section 18). Six call sites use the unsafe variant: the end of mark-all-read, four typing notifications and one presence update (`zerver/actions/message_flags.py:92`, `zerver/actions/typing.py:57`, `zerver/actions/typing.py:133`, `zerver/actions/typing.py:177`, `zerver/actions/typing.py:213`, `zerver/actions/presence.py:82`). The apply logic treats typing events as transient (`zerver/lib/events.py:1824-1829`).
- [code] **Message events.** Inside `do_send_messages`, after the rows are written, each message gets a "wide" dict and a list of per-user dicts (id, flags, mentioned group) with the sender first, so the sender is served first when there are thousands of recipients (`zerver/actions/message_send.py:1233-1237`, `zerver/actions/message_send.py:1257-1290`). The event also carries data only Tornado needs (idle users, push and email sets, guest ids, realm host) and, for public channels, the stream name and realm so Tornado can serve clients that watch all public channels (`zerver/actions/message_send.py:1333-1359`, `zerver/actions/message_send.py:1361-1381`). The publish call is `zerver/actions/message_send.py:1417-1421`.
- [doc] Tornado does no database work, so the send path precomputes everything Tornado needs (`docs/subsystems/sending-messages.md:90-95`, `docs/overview/architecture-overview.md:79-92`). The caller is responsible for choosing the user list correctly; sending direct-message content to the whole organisation is named as the failure to avoid (`docs/subsystems/events-system.md:74-78`).
- [code] **Routing and fan-out in Tornado.** `process_notification` dispatches on event type to specialised handlers, and a default handler offers the event to every queue of every listed user (`zerver/tornado/event_queue.py:1790-1842`, `zerver/tornado/event_queue.py:1414-1418`). For messages, `get_client_info_for_message_event` collects the queues of each listed user plus queues registered for all public channels in that realm, excluding guests for channels that are not web-public (`zerver/tornado/event_queue.py:1091-1136`). Each queue then filters with `accepts_event` (event-type subset, narrow predicate, capability-gated variants) (`zerver/tornado/event_queue.py:245-283`). The per-capability message payload is built once and reused across queues (`zerver/tornado/event_queue.py:1234-1249`).
- [code] **Batching.** The send function takes a list of requests and bulk-inserts messages and per-user rows in one transaction (`zerver/actions/message_send.py:1042-1063`, `zerver/actions/message_send.py:1134`). The RabbitMQ consumer in Tornado is fixed at one notice per callback (`zerver/lib/queue.py:422-434`). Delete events carry a sorted list of message ids per conversation rather than one event per message (`zerver/lib/retention.py:352-362`), with a per-message fallback only for old clients (`zerver/tornado/event_queue.py:1432-1445`). Read-flag events are merged in the queue (above), and fetches are capped at 5000 messages (Section 4).
- [code] Only the sending client's queue receives `local_message_id`, so it can swap its locally echoed message for the real one (`zerver/tornado/event_queue.py:1103-1106`, `zerver/tornado/event_queue.py:1342-1345`); the web client reads it in `web/src/server_events.js:72-74`.
- [code] **Event identity.** Tornado assigns the integer `id` when it pushes an event onto a queue: a per-queue counter that starts at 0. Producers never supply it (`zerver/tornado/event_queue.py:362-363`, `zerver/tornado/event_queue.py:392-401`), and the schema checker strips it before validating the domain payload (`zerver/lib/event_schema.py:132-136`).
- [doc] The API reference says ids are increasing but not consecutive (`zerver/openapi/zulip.yaml:410-413`). [code] One source of gaps: read-flag events are merged into a single "virtual" event that keeps only the latest id (`zerver/tornado/event_queue.py:402-429`, `zerver/tornado/event_queue.py:449-469`), pinned by a test (`zerver/tests/test_event_queue.py:1393-1420`). - [code] **Schemas.** Event payloads are pydantic models that forbid undeclared fields (`zerver/lib/event_types.py:25-32`); sending converts a model to a dict and drops unset optional fields so the wire shape stays unchanged (`zerver/tornado/django_api.py:224-247`). The legacy-dict path is still accepted while call sites are migrated (comment, `zerver/tornado/django_api.py:220-223`). Policy: every event generated by the API is validated by a test with a checker (`zerver/lib/event_schema.py:1-5`).
- [code] **Versioning.** Capabilities declared at register decide which event variants a queue receives (`zerver/lib/events.py:2083-2103`, `zerver/tornado/views.py:253-275`, `zerver/tornado/event_queue.py:1421-1445`). [doc] New fields are documented with an API feature level, incompatible changes are gated by a capability, and events already sitting in Tornado's queue at upgrade time need translation code (`docs/subsystems/events-system.md:419-442`, `docs/subsystems/events-system.md:445-457`); an example of that translation is `zerver/tornado/event_queue.py:1151-1190`.
- [code] **Absence of a durable log.** The word "outbox" appears in application Python only as Django's email test outbox in test helpers and settings (`zerver/lib/test_classes.py:1036-1049`, `zproject/test_extra_settings.py:67`) and as a variable name in one webhook (`zerver/webhooks/front/view.py:17`); there is no outbox table. The notification queue is RabbitMQ with persistent messages (`zerver/lib/queue.py:126-135`); the event itself is not stored in the application database. Not found: any component that re-reads the database to reconcile a queue (a search for `reconcil` in `zerver/tornado`, `zerver/lib/events.py` and `zerver/lib/queue.py` returns nothing).
- [inference] The contract has two layers: a typed, tested domain payload and a transport envelope id added by the queue. The separation is right for us. The mistake to avoid is letting the transport assign the identity clients use for ordering and dedupe, because that identity is then not stable across consumers, retries or restarts.

## 9. Reconnect, recovery and duplicates

- [code] **Register: the initial-state versus subscription race.** `do_events_register` (a) asks Tornado to create the queue, (b) fetches the full state with ordinary, non-atomic queries, (c) asks Tornado for everything already queued (`last_event_id` of -1) and (d) applies those events to the fetched state with `apply_events` (`zerver/lib/events.py:2196-2258`, `zerver/tornado/django_api.py:86-150`, `zerver/tornado/django_api.py:153-175`). The returned `last_event_id` is the id of the last event applied, or -1 (`zerver/lib/events.py:2264-2267`). [doc] Same algorithm, and the reason non-atomic reads are acceptable (`docs/subsystems/events-system.md:189-222`).
- [inference] Why it works: the queue exists before any state is read, so a change committed after queue creation reaches the queue, and a change committed before is in the state. A change that straddles the two (committed after queue creation but visible to a later state query) is in both, so applying an event to a state that already reflects it must be harmless. The design needs idempotent apply, not atomic reads.
- [code] The apply branches for messages and unread state use max, keyed assignment and pop-with-default (`zerver/lib/events.py:1032`, `zerver/lib/message.py:1233`, `zerver/lib/message.py:1280-1287`). Many other branches append or extend a list with the event's items and no membership check, for example saved snippets, navigation views, drafts, scheduled messages, reminders, realm bots, starred ids, realm domains, user groups and group members and subgroups (`zerver/lib/events.py:1075`, `zerver/lib/events.py:1089`, `zerver/lib/events.py:1103`, `zerver/lib/events.py:1133`, `zerver/lib/events.py:1168`, `zerver/lib/events.py:1376`, `zerver/lib/events.py:1854`, `zerver/lib/events.py:1863`, `zerver/lib/events.py:1923`, `zerver/lib/events.py:1932`, `zerver/lib/events.py:1942`). [inference] The first group tolerates repeats. For the second group, if such a change committed between queue creation and the matching state query, the entry would appear twice. I did not execute this.
- [code] **Acknowledgement.** The register response's `last_event_id` equals the last applied event, and the client's first poll passes it, which prunes those events from the queue (`zerver/lib/events.py:2264-2267`, `web/src/server_events.js:172-175`, `zerver/tornado/event_queue.py:832`).
- [code] **Poll.** `GET /events` carries `queue_id` and `last_event_id`. `fetch_events` finds the queue (unknown queue or wrong user raises `BadEventQueueIdError`), rejects an id older than the newest pruned one, prunes through `last_event_id`, rejects an id the queue never held, then returns every event still queued or parks the request as the queue's single waiting handler (`zerver/tornado/event_queue.py:798-874`, `zerver/tornado/event_queue.py:528-540`). Events are not removed when sent: `contents()` leaves them in place and only a later poll's `last_event_id` prunes (`zerver/tornado/event_queue.py:218-243`, `zerver/tornado/event_queue.py:444-447`, `zerver/tornado/event_queue.py:449-473`). A lost response is recovered by repeating the same `last_event_id`. A test pins ack-then-only-newer behaviour and the sender-only `local_message_id` (`zerver/tests/test_event_system.py:437-526`).
- [inference] Ordering hazard: `prune` runs at line 832, before the "event was not in this queue" check at lines 833-841 of the same function, so a client that acknowledges an id beyond the queue head makes the queue discard its pending events and then returns an error. No test pins either error message (a search for `already been pruned` and `was not in this queue` in `zerver/tests` returns nothing). An acknowledgement validator for us should reject before it mutates.
- [code] **Client advance.** The web client moves `last_event_id` to the highest id in each batch before it dispatches the batch, logs and swallows an exception per event, then polls again (`web/src/server_events.js:45-51`, `web/src/server_events.js:94-100`, `web/src/server_events.js:192-204`). [inference] An event whose handler throws is acknowledged and not retried; only a later reload repairs that client.
- [code] **Heartbeat and retry.** A parked poll gets a heartbeat event after 45 seconds plus up to 10 seconds of jitter, and that heartbeat consumes an event id (`zerver/tornado/event_queue.py:62-71`, `zerver/tornado/event_queue.py:302-318`). The client treats a timeout as a plain retry, other failures as back-off, and shows a banner after eight consecutive failures; after any failure the next request is non-blocking and the client marks itself suspect-offline (`web/src/server_events.js:163-171`, `web/src/server_events.js:221-246`).
- [code] **Expiry.** A sweep every minute removes queues that have no connected handler and whose last connection is older than their timeout: 10 minutes by default, caller-chosen up to 7 days, 12 hours for the mobile profile (`zerver/tornado/event_queue.py:45-60`, `zerver/tornado/event_queue.py:137-143`, `zerver/tornado/event_queue.py:289-293`, `zerver/tornado/event_queue.py:634-655`, `zerver/tornado/event_queue.py:789-791`). A comment records why the default fell from a week: queues of dead browser sessions grew large (`zerver/tornado/event_queue.py:42-45`). No cap on a live queue's length was found (a search for `MAX_`, `maxlen` and `overflow` in the file finds only timeouts).
- [code] **Bad queue id leads to a full reload.** A missing queue and a queue owned by another user raise the same error, code `BAD_EVENT_QUEUE_ID` (`zerver/tornado/exceptions.py:7-17`, `zerver/tornado/event_queue.py:528-540`). The web client answers an HTTP 400 with that code by reloading at once and saving the compose box, which re-runs register and the first message fetch (`web/src/server_events.js:210-219`). [doc] The API reference tells every client to re-initialise (`zerver/openapi/zulip.yaml:6850-6857`, `zerver/openapi/zulip.yaml:18360-18366`). Tests pin the unknown and wrong-owner cases (`zerver/tests/test_event_system.py:772-816`).
- [code] **Restart.** On shutdown Tornado dumps all queues to a JSON file and on start loads them and schedules a rolling reload event for web clients (`zerver/management/commands/runtornado.py:139-141`, `zerver/tornado/event_queue.py:685-734`, `zerver/tornado/event_queue.py:750-776`). [doc] A crash that loses the queues is described as acceptable because clients recover as if they had been offline (`docs/subsystems/events-system.md:164-176`).
- [code] **Where duplicates can come from.** RabbitMQ is acknowledged after the Tornado handler returns, so a crash between processing and ack redelivers the notification (`zerver/lib/queue.py:422-430`). A failing handler re-publishes the whole notification up to three times, to every recipient queue again, and then logs and drops it (`zerver/tornado/event_queue.py:1851-1866`, `zerver/lib/queue.py:26`, `zerver/lib/queue.py:510-519`). [inference] In both cases the repeated event gets a fresh queue event id, so the id cannot be used to dedupe; the final protection is at the message level, where the client drops a message whose id it already holds (`web/src/message_list_data.ts:226-229`, `web/src/message_list_data.ts:313-315`) and logs an error if a duplicate reaches its index (`web/src/message_list_data.ts:558-568`).
- [doc] The docs aim for "exactly-once" delivery (`docs/subsystems/events-system.md:39-40`, `docs/subsystems/events-system.md:138-144`). The code gives at-least-once between a queue and its client (events stay until acknowledged), and the paths above show duplicates are possible earlier in the chain. See Appendix A.
- [code] **History versus events in the client.** While the first message fetch is in flight, the client stores incoming events and replays them afterwards (`web/src/server_events.js:24-26`, `web/src/server_events.js:53-61`, `web/src/server_events.js:266-271`, `web/src/message_fetch.ts:759-770`, `web/src/ui_init.js:677-681`). Later, a new message that arrives while the list does not yet reach the newest end is not appended but its id is remembered, and if a fetch that reports "newest" returns a lower maximum id the client fetches again (`web/src/message_list_data.ts:341-346`, `web/src/fetch_status.ts:25-31`, `web/src/fetch_status.ts:72-128`). [doc] A doc paragraph says clients must discard message events for messages they have not fetched (`docs/subsystems/events-system.md:405-412`).
- [code] Not found: any way for a client to detect an event lost between the database commit and the queue. Event ids are assigned after that point, so a dropped notification leaves no visible gap. [inference] The loss is repaired only when the user reloads.

## 10. Tenant (realm) boundaries

- [code] Every message row carries a realm foreign key, documented as important for indexes and sharding; cross-realm bots are the stated exception (`zerver/models/messages.py:33-38`). [doc] A realm maps to a subdomain of the server (`docs/subsystems/realms.md:37-45`).
- [code] Queries enforce the realm explicitly in three places: the base search query filters by realm when no per-user join is used, the access check refuses public-stream messages from another realm, and the bulk stream-access query filters by realm (`zerver/lib/narrow.py:972-973`, `zerver/lib/message.py:608-610`, `zerver/lib/message.py:789`). With the per-user join, a comment says the realm is deliberately not filtered because the user filter is more selective (`zerver/lib/narrow.py:990-995`).
- [code] Event routing uses the realm only to choose a Tornado shard (`zerver/tornado/sharding.py:25-34`, `zerver/tornado/django_api.py:258-265`). Queues are keyed by global user id, and the all-public-channels index is keyed by realm id (`zerver/tornado/event_queue.py:543-548`, `zerver/tornado/event_queue.py:1110-1123`); a queue stores its realm id and user id (`zerver/tornado/views.py:253-255`).
- [inference] Realtime isolation depends on the writer producing the right user list and on the queue being bound to its owner (`zerver/tornado/event_queue.py:528-540`); there is no second tenant check in the delivery layer. For us the tenant id belongs in the channel name and in subscription authorisation, not only in the caller's list.

## 11. Attachments

- [code] An attachment row has a unique path id, owner, realm, size, content type and cached public and web-public flags (`zerver/models/messages.py:728-763`). A message "claims" files referenced in its text inside the send transaction, only if the sender may access each file; a refused claim is logged and skipped, and the owner gets an update event on commit (`zerver/actions/message_send.py:1065-1096`, `zerver/actions/uploads.py:29-80`).
- [code] Access to a file is checked by `validate_attachment_request`, which also has a path for logged-out spectators (`zerver/lib/attachments.py:106-124`). Unclaimed files older than a configurable number of weeks are cleaned up, never those still referenced by any live, scheduled or archived message (`zerver/lib/attachments.py:233-262`).
- [code] Archiving a message moves its attachment links with it, and the attachment row itself only when its last message goes (`zerver/lib/retention.py:296-315`).
- [inference] Nothing here needs adopting for the realtime design; the useful pattern is "claim inside the message transaction, clean up unclaimed later".

## 12. Authorization and audit

- [code] Access to a message by id requires a per-user row or public-channel access, and failures return one generic error so existence is not leaked (`zerver/lib/message.py:399-448`, `zerver/lib/message.py:581-631`). The helper that chooses recipients of delete, react and similar events mirrors that access function (`zerver/lib/message.py:634-660`).
- [code] A queue can be used only by its owner (`zerver/tornado/event_queue.py:528-540`); a test pins the wrong-user case (`zerver/tests/test_event_system.py:787-816`).
- [code] Audit is a realm-level log: event type, acting user, modified user, stream or group, time and a JSON blob, written in the same transaction as the change (`zerver/models/realm_audit_logs.py:162-181`, `zerver/models/realm_audit_logs.py:216-245`, `zerver/actions/streams.py:185-192`). Not found: audit events for sending, editing or reading a message (a search for `MESSAGE` in the audit enum file returns only user-deletion and retention-setting types: `zerver/models/realm_audit_logs.py:23`, `zerver/models/realm_audit_logs.py:102`). Edits keep an edit history on the message row (`zerver/models/messages.py:105-107`).
- [inference] Zulip splits audit (administrative changes, durable) from message history (the messages themselves). We need a third thing, actor-stamped conversation events such as assignment and status changes, which Zulip has no model for.

## 13. Transaction boundaries and concurrency

- [code] **Send.** `do_send_messages` is one atomic block: bulk insert of messages, attachment claims, bulk insert of per-user rows, bot-queue and embed-link jobs enqueued on commit, and the realtime event published on commit (`zerver/actions/message_send.py:1042-1063`, `zerver/actions/message_send.py:1134-1148`, `zerver/actions/message_send.py:1417-1454`). No row lock is taken on the channel or recipient, so concurrent senders to one conversation do not serialise (a search for `select_for_update` in the file returns nothing). [doc] The docs list the same set of effects as done atomically (`docs/subsystems/sending-messages.md:78-102`).
- [code] **Publish on commit, with exceptions.** The durable path publishes after commit. Mark-all-read spans many transactions, so it publishes once after the loop with the unsafe variant; typing and presence use the unsafe variant because they are ephemeral (Section 8).
- [code] After commit, publication is a best-effort call: it tries once, reconnects and tries a second time, and a second failure raises out of the commit callback (`zerver/tornado/django_api.py:292`, `zerver/lib/queue.py:137-146`). [inference] If the process dies between commit and publish, or the broker stays unreachable, the event is lost and no stored record remains to resend; a transactional outbox closes that window. I did not execute a crash, and I did not check how the request layer reports the raised error.
- [code] **Register** crosses two services and is not transactional; correctness comes from the queue-first ordering described in Section 9. The Django-to-Tornado POSTs are retried up to three times (`zerver/tornado/django_api.py:31-37`).
- [code] **Edit.** The edit path locks the message row, and an optional `prev_content_sha256` makes a stale edit fail with an error; a test pins the second writer losing (`zerver/actions/message_edit.py:177-180`, `zerver/actions/message_edit.py:1788-1805`, `zerver/tests/test_message_edit.py:2598-2636`). Callers that omit the hash get last-writer-wins.
- [code] **Flags.** Row locks, bit operations and a filter that skips rows already in the target state make repeated or concurrent flag updates converge (`zerver/actions/message_flags.py:346-363`, `zerver/actions/message_flags.py:401-407`).
- [code] **Delete and archive** move rows and send the delete event inside the same chunked transaction, so the event exists only if the move committed (`zerver/lib/retention.py:159-172`, `zerver/lib/retention.py:402-413`).
- [doc] The project's rule: a read-then-write that depends on what it read needs a row lock; take locks in a consistent order to avoid deadlocks; keep the locked transaction short; always state `no_key=` explicitly and enforce it with a linter (`docs/subsystems/database-concurrency.md:5-9`, `docs/subsystems/database-concurrency.md:33-60`).
- [code] **History fetch** uses a read-only repeatable-read transaction (`zerver/views/message_fetch.py:209-232`).
- [inference] Zulip's design avoids per-conversation serialisation entirely, which is why it cannot offer a per-conversation sequence. Our send path accepts a short lock on the conversation row in exchange for a gap-free sequence.

## 14. Background jobs and retention

- [code] Deferred work runs in RabbitMQ-backed workers that register themselves by queue name, with one module per kind of job under `zerver/worker/` (embed links, deferred work, missed-message emails, mobile notifications, outgoing webhooks and others) (`zerver/worker/base.py:54-77`). A failed batch is logged and appended to a per-queue `.errors` file (`zerver/worker/base.py:253-288`). Work triggered by a message is enqueued on commit (`zerver/actions/message_send.py:1423-1430`, `zerver/actions/message_send.py:1445-1454`).
- [code] Tornado's own notice queue retries a failing notice three times and then drops it with an error log (`zerver/lib/queue.py:26`, `zerver/lib/queue.py:510-519`, `zerver/tornado/event_queue.py:1851-1857`).
- [code] Retention is a management command that first vacuums expired archive data, then archives messages past each realm's or channel's retention in chunks, then cleans attachments (`zerver/management/commands/archive_messages.py:13-19`, `zerver/lib/retention.py:545-555`); the schedule that runs it was not examined.
- [code] Queue garbage collection is a periodic Tornado callback, once a minute (`zerver/tornado/event_queue.py:46-48`, `zerver/tornado/event_queue.py:789-791`).
- [inference] The pattern "durable queue, worker, error file" is a standard job runner. We need an outbox relay with retry and a dead-letter table instead of an error file.

## 15. Testing and performance strategies

- [doc] The event-system doc prescribes a test protocol for the register race: fetch state, run the action, capture the events, apply them to the stale state, fetch fresh state, and compare (`docs/subsystems/events-system.md:263-281`). [code] `BaseAction.verify_action` implements it: a state fetched before the action plus the action's events must equal a state fetched after, the events must validate against the API schema, and a test whose events change nothing is rejected as too weak (`zerver/tests/test_events.py:338-344`, `zerver/tests/test_events.py:413-514`). The helper runs the on-commit callbacks so publication is exercised (`zerver/tests/test_events.py:436-440`). `verify_action(` occurs 343 times in the file (command in Section 18).
- [inference] That test covers one interleaving only: the state is fetched before the change. It does not cover the straddling case where the state already reflects the change and the event still arrives, which is the case that exposes non-idempotent apply branches (Section 9). It also never delivers an event twice or out of order. I found no randomised or multi-thread interleaving test for the event path (a search for `Thread(` and `threading` in the event, queue, message and retention tests found no thread use; the only hits were a topic title containing the word).
- [code] The queue itself has unit tests: id assignment and round-trip through dict form, collapsing of read-flag events with ids, virtual-event reconstruction, garbage collection and offline marking (`zerver/tests/test_event_queue.py:1352-1370`, `zerver/tests/test_event_queue.py:1372-1454`, `zerver/tests/test_event_queue.py:1538-1585`, `zerver/tests/test_event_queue.py:1702-1741`). Integration tests cover poll and ack (`zerver/tests/test_event_system.py:387-526`) and bad or foreign queue ids (`zerver/tests/test_event_system.py:772-816`).
- [code] The only ordering evidence is in the queue unit tests: ids are assigned in push order starting at 0, and a merged read-flag event sits at the position of its latest id (`zerver/tests/test_event_queue.py:1372-1454`). [inference] No test asserts message order within a queue: the nearby two-message check in `zerver/tests/test_event_system.py:517-526` compares only count, sender, recipient and the absence of `local_message_id`, and both messages have identical content, so a swapped order would pass. No test asserts ordering under concurrent senders or across several queues.
- [code] The anchor logic has a pure-function test table (`zerver/tests/test_message_fetch.py:1507-1560`) inside a file of 185 test methods (`grep -c "def test_"`).
- [code] Performance engineering is query counting: the send path asserts exact query counts for common cases, and the register path asserts a total of 48 queries and a per-event-type count (`zerver/tests/test_message_send.py:1882-1889`, `zerver/tests/test_event_system.py:1553-1630`). [doc] The docs state that every send query is a bulk query and is tested for count (`docs/subsystems/sending-messages.md:99-102`). Other measures: payload built once per capability set, sender served first, per-user flags computed in bulk (`zerver/tornado/event_queue.py:1234-1249`, `zerver/actions/message_send.py:1260-1266`).
- [code] Not found: load or throughput tests of the event path (a search for `locust`, `loadtest`, `load-test`, `load_test`, `wrk`, `jmeter` and `gatling` over `tools`, `docs`, `zerver`, `scripts` and `puppet` returned two unrelated files: an upload-test fixture name and a Grafana webhook payload).

- [inference] For our design: copy the discipline (every outbox event type has a schema and a test that fails when a producer is added without one) and add what Zulip lacks (duplicate, reorder and straddle tests of the client merge, and a crash test of the relay).

## 16. Synchronization invariants for our platform

- [inference] **What is not copied.** Zulip's long-polling event queues and its Tornado server are not copied and are not proposed for reuse. That means no per-client server-side queue, no `GET /events` long poll, no queue garbage collection or persistence file, no server-side `apply_events` replay and no compaction of read events. Our delivery is the transactional outbox to Centrifugo channels (durable events, at least once) plus API catch-up with `?after=<lastSequence>`; Centrifugo's own history and recovery stay an optimisation, and when they fail the client reloads from the API. What transfers from Zulip is the protocol discipline it arrived at, not its machinery.
- [inference] **What transfers and what does not.** The Zulip column of each row below is [code] or [doc] as cited; the other two columns are my design judgement.

| Zulip mechanism | Evidence | Our mechanism (Centrifugo plus API catch-up) | Transfers? |
|---|---|---|---|
| Create the queue before reading state, then apply what was queued | `zerver/lib/events.py:2196-2258` | Subscribe to the conversation channel first, fetch history, merge by `sequence` | The ordering rule, yes; the queue, no |
| Acknowledge with the highest id received; unacknowledged events are replayed | `zerver/tornado/event_queue.py:444-447`, `zerver/tornado/event_queue.py:798-874` | Client persists its highest contiguous `sequence` per conversation; replay comes from Centrifugo recovery or `?after=` | The idea, yes; the server-held queue, no |
| Unknown or expired queue leads to a full reload | `web/src/server_events.js:210-219` | Continuity that cannot be proven (recovery reported as failed, refused or expired subscription, a gap a delta fetch cannot fill, an API head below the client's cursor) leads to a full API load of the newest page; a fillable gap or successful recovery is a `?after=` delta merge (SI-4) | The full reload, yes; the delta path is ours |
| Server applies queued events to the state it fetched | `zerver/lib/events.py:976-1066` | Client merges API snapshot and events by `sequence` | No |
| Event id is a per-queue counter assigned after commit | `zerver/tornado/event_queue.py:392-401` | `eventId` from the outbox row and `sequence` from the database transaction | No (this is the main thing to do differently) |
| Client buffers events during the first fetch | `web/src/server_events.js:53-61` | Same | Yes |
| Remember the highest id seen and refetch if a response is behind | `web/src/fetch_status.ts:72-128` | Buffer events during the fetch, apply the contiguous ones above the response head, fetch only for a gap (SI-8) | The detection idea, yes; discard-and-refetch, no |
| Heartbeats and queue garbage collection | `zerver/tornado/event_queue.py:302-318`, `zerver/tornado/event_queue.py:634-655` | Transport concerns of Centrifugo | No |
| Typed schema and a test for every event type | `zerver/lib/event_schema.py:1-5`, `zerver/tests/test_events.py:413-514` | Same, extended with duplicate and reorder cases | Yes |

Each invariant below states a rule, the Zulip evidence that motivates it, and a test that can fail. They are all [inference] drawn from the [code] and [doc] items cited.

- [inference] **SI-1 Subscribe, then snapshot, then apply newer.** A client MUST have an active subscription to a conversation's realtime channel before it sends the history request for that conversation. It MUST apply to the snapshot every buffered or later event whose `sequence` is above the snapshot's highest sequence, and drop events at or below it. Evidence: the queue exists before state is read (`zerver/lib/events.py:2196-2258`), and the client buffers events during its first fetch (`web/src/server_events.js:53-61`). Test: an integration test publishes message N after the subscribe call; run once with N committed before the history query runs (N is in the snapshot and also arrives as an event) and once after (N arrives only as an event). The final list contains N exactly once in both runs.
- [inference] **SI-2 The database assigns a stable, monotonic, gap-free, per-conversation `sequence`.** This is our design decision (overview D4, in `docs/superpowers/plans/2026-10-27-conversation-platform-00-overview.md`, as ratified by the controller), not a Zulip finding: `sequence` is `conversations.last_sequence + 1`, computed inside the message transaction while holding the conversation row lock. It is not a PostgreSQL SEQUENCE, whose values can skip after a rollback, so the committed messages of a conversation are numbered 1, 2, 3 with no gap. Message tombstones keep their sequence, and purge removes whole conversations' messages and archives the conversation, so a conversation never keeps a hole in the middle. The outbox relay, Centrifugo and clients never assign or change it; it is our `last_event_id` equivalent. Evidence for why we differ from Zulip: its id is assigned by the delivery layer after commit, per queue, and is not consecutive (`zerver/tornado/event_queue.py:392-401`, `zerver/openapi/zulip.yaml:410-413`), and its message id is not commit-ordered (`zerver/actions/message_send.py:1042-1063`). Test: 50 concurrent sends to one conversation produce sequences 1 to 50 with no duplicate and no gap; a send that rolls back leaves no hole; restarting the relay changes no sequence. Which events carry which counter is settled in the ruling at the end of this section (messages only).
- [inference] **SI-3 A client detects gaps and duplicates by `sequence`.** For each conversation the client keeps `lastContiguous`. On an event with sequence `s`: if `s` is at most `lastContiguous`, ignore it; if `s` equals `lastContiguous + 1`, apply it and advance; if `s` is larger, do not apply it and fetch `?after=<lastContiguous>` from the API. Evidence for the need: a Zulip client cannot see a lost event because ids are assigned after the loss (Section 9) and it relies on message-id dedupe alone (`web/src/message_list_data.ts:226-229`). Test: from cursor 4, deliver 7 only: the client requests `after=4` and ends with 5, 6, 7. From cursor 4, deliver 5 and then 7: the cursor moves to 5, the client requests `after=5` and ends with 5, 6, 7. Deliver 5 twice: one copy.
- [inference] **SI-4 Recover by delta when continuity can be restored; reload from the API when it cannot be proven; never rebuild from client memory.** Two cases. (a) Delta catch-up. Triggers: a gap seen on a live subscription (SI-3), successful Centrifugo recovery (the replayed events are applied under SI-3), or a reconnect whose delta fetch closes the gap (the response begins at `lastContiguous + 1` and reaches the head). Action: fetch `?after=<lastContiguous>` until `hasMore` is false and merge into the local copy by `sequence`. (b) Full reload. Triggers: Centrifugo recovery reported as failed (`recovered=false`), a subscription refused or expired, a gap the delta fetch does not fill (the response does not begin at `lastContiguous + 1`, or is still non-contiguous after one retry), a failed apply (SI-6), or an API head below the client's `lastContiguous` (SI-9). Action: discard the local copy of that conversation's server state and load the newest page from the API. In case (b) the client MUST NOT rebuild from in-memory buffers, earlier event payloads or a local copy of server state. User-typed unsent drafts are not server state and are kept, as Zulip keeps the compose box. Evidence: Zulip has only case (b), reloading on a bad queue id (`web/src/server_events.js:210-219`, `docs/subsystems/events-system.md:159-167`, `zerver/openapi/zulip.yaml:6850-6857`); case (a) is ours and rests on the sequence of SI-2. Test: (a) drop sequence 6 between 5 and 7 and assert one `after=5` request, a merged list 5, 6, 7 and a kept local copy; (b) clear Centrifugo's history for the channel while the client is offline, reconnect with `recovered=false`, and assert a newest-page API load ending equal to a fresh load; plant a stale local cache and assert it is never read in case (b).
- [inference] **SI-5 Events carry stable ids, so duplicates are idempotent.** Every durable event carries an `eventId` (the outbox row id, identical on every redelivery) plus `conversationId` and `sequence`. Applying an event twice, in any interleaving that respects sequence order, gives the same state as applying it once; updates that append to a list must be keyed. Evidence: a redelivered Zulip notification gets a new queue id, so dedupe falls to the message id (`zerver/lib/queue.py:422-430`, `zerver/tornado/event_queue.py:1851-1866`, `web/src/message_list_data.ts:226-229`), and many apply branches append without a key (Section 9; for example `zerver/lib/events.py:1075`, `zerver/lib/events.py:1854`). Test: a property test inserts random duplicates into a random event stream, for every event type's reducer, and asserts equality with the duplicate-free run.
- [inference] **SI-6 The cursor advances only after a successful apply.** The client persists `lastContiguous` after the event has been applied to its state. A failed apply does not advance the cursor and triggers a full reload of that conversation (SI-4 case b) instead of skipping the event. Evidence: the Zulip web client advances before it dispatches and swallows per-event errors (`web/src/server_events.js:45-51`, `web/src/server_events.js:94-100`). Test: make the reducer throw on sequence 7; assert the cursor stays at 6 and the conversation does a full API load of the newest page.
- [inference] **SI-7 An event is published if and only if its transaction committed, and a committed event is eventually published.** The outbox row is inserted in the same transaction as the change; a relay publishes it and marks it published only after Centrifugo accepted it. Evidence: Zulip's on-commit hook gives "only if committed" (`zerver/tornado/django_api.py:275-292`) but not "eventually", because the publish after commit is a single best-effort call with one retry (`zerver/lib/queue.py:137-146`). Test: (a) roll back after the outbox insert and assert nothing is published; (b) kill the relay between commit and publish and assert the event arrives after restart with the same `eventId`; (c) kill it after publish and before marking and assert the event arrives twice with the same `eventId` and the client applies it once (SI-5).
- [inference] **SI-8 A history response is reconciled with the events buffered while it was in flight.** After a history response with head `h` is applied, the client applies the buffered events with sequence above `h`, in order and with no extra fetch, as long as they are contiguous from `h + 1`; events at or below `h` are dropped as duplicates. If the buffer is not contiguous from `h + 1`, the gap rule of SI-3 fetches `?after=<lastContiguous>`. The client counts as caught up only when `lastContiguous` is at least the highest sequence seen on the channel. No special case for deleted rows is needed, because tombstones keep their sequence (SI-2). Evidence: Zulip has no buffer after its first fetch; it drops such messages, remembers the highest dropped id and refetches if the response is behind (`web/src/fetch_status.ts:25-31`, `web/src/fetch_status.ts:72-128`). We buffer because we subscribe first (SI-1), so the common outcome needs no refetch. Test: publish message N+1 between the history query and the processing of its response; the client ends with N+1 applied from its buffer, and the API call count for that conversation is exactly one.
- [inference] **SI-9 A bad cursor never changes or discards server data.** Two server-side cases. The catch-up read `?after=<seq>` validates its cursor first: a value beyond the conversation head returns an empty page and the current head, with no state change. The read-cursor write endpoint is monotonic and clamped: it stores the greater of the stored and the reported value (overview D13), clamps the reported value to the conversation's last sequence, never moves the cursor backwards, and returns the stored cursor and the head. One client-side case: if the head returned by the API is below the client's `lastContiguous`, the client's copy is ahead of the server and it takes case (b) of SI-4. Evidence: Zulip prunes before it checks the acknowledgement (`zerver/tornado/event_queue.py:832-841`). Test: `after = head + 100` returns 200, an empty list and the head; a read cursor reported as head + 100 is stored as head; a lower reported value leaves the stored cursor unchanged; a client with `lastContiguous = 20` that receives head 15 does a full load of the newest page.
- [inference] **SI-10 Durable and ephemeral events are separate classes.** Typing, presence and similar signals are published directly with no outbox row and no sequence; losing them changes no stored or derived state. Durable events never depend on them. Evidence: Zulip sends these with the unsafe publisher and ignores typing when applying state (`zerver/actions/typing.py:57`, `zerver/actions/presence.py:82`, `zerver/lib/events.py:1824-1829`). Test: drop every ephemeral message in a run and assert the final client state is unchanged.
- [inference] **SI-11 Audience and tenant are decided by the writer and encoded in the channel name.** The audience of a durable event is derived in the same service call that authorises the write; the channel name contains the tenant id; a subscription to another tenant's channel, or to a conversation the principal may not see, is refused. Evidence: the caller picks the user list and the delivery layer has no second tenant check (`docs/subsystems/events-system.md:74-78`, `zerver/tornado/event_queue.py:528-540`). Test: a cross-tenant subscribe is refused; a tenant-A event is published and no tenant-B subscriber receives it.
- [inference] **SI-12 Snapshot plus events equals a fresh snapshot.** For every event type, the state built from a snapshot at sequence `s` plus events `s+1..n` equals the state of a fresh snapshot at `n`, including when an event is delivered before the snapshot response and when events are duplicated. Evidence: Zulip pins one interleaving only (`zerver/tests/test_events.py:413-514`). Test: the property test from SI-5 run with the three interleavings (event before snapshot, after, straddling).
- [inference] **SI-13 History pages are bounded and internally consistent.** The history endpoint caps page size, returns `hasMore` and the conversation head sequence, and reads the page from one snapshot. Evidence: Zulip caps at 5000 and runs the page in a read-only repeatable-read transaction (`zerver/views/message_fetch.py:35`, `zerver/views/message_fetch.py:152-157`, `zerver/views/message_fetch.py:209-232`). Test: a request over the cap fails with 400; a concurrent insert during the read never produces a page with a hole.

- [inference] **Which invariants transfer from Zulip.** Direct transfers of a Zulip discipline: SI-1 (queue before state, as subscribe before history), SI-10 (ephemeral events apart), SI-12 (snapshot-plus-events test) and SI-13 (consistent, capped pages). Transfers with a different mechanism: SI-3 and SI-5 (Zulip dedupes by message id; we dedupe by `eventId` and `sequence`), SI-4 (Zulip's reload on a bad queue id is our case b; the delta path of case a is ours), SI-8 (Zulip drops and refetches; we buffer and apply) and SI-11 (Zulip's caller-chosen user list becomes a tenant-scoped channel name). Where we deliberately do what Zulip does not: SI-2 (a database-assigned sequence), SI-6 (acknowledge after apply), SI-7 (the outbox gives "eventually published") and SI-9 (validate before mutate). All thirteen rely only on Centrifugo channels, its short history as an optimisation, and our API; none relies on a long-poll queue or on Tornado.

**Open points and rulings** (design decisions for Task 7, not Zulip findings). Controller ruling, Plan 01 ledger: `sequence` numbers messages only. `conversation.created` and `conversation.updated` events carry the conversation `version`, which is monotonic per conversation. Typing events carry neither. A `version` jump greater than 1 on a conversation event triggers a refetch of the conversation view. This settles the earlier question whether status, assignment and read-cursor events share the message sequence: they do not. Zulip, by contrast, puts every event type on one per-queue counter (`zerver/tornado/event_queue.py:392-401`).
