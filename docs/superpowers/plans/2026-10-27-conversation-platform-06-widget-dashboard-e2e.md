Depends on Plans 02–05 (the full backend API).

**Goal:** Move the existing Lit widget and Next.js dashboard onto the new tenant-scoped APIs and realtime contracts, with pending/retry sends, typing, presence, lifecycle actions, cursor-paginated history, read cursors and reconnect reconciliation; replace the demo module and contracts; and prove the master-spec 12.3 scenario plus the 14.5 resilience cases with Playwright in two browser contexts against the real stack.

**Architecture:** `libs/chat-client` stays framework-agnostic (no React/Lit) and owns: typed APIs (widget/agent), session storage, Centrifuge wiring, the conversation sync algorithm (subscribe → catch-up by `sequence` → gap detection → dedupe by `eventId`/message id), the pending-message queue (stable `clientMessageId`, retry), and typing helpers. The widget and dashboard render state from those helpers. The `chat` backend module and `/api/v1/demo/*` are deleted in T4.

**Tech Stack:** Lit 3.3.3, Next.js 16.4.3 / React 19, `centrifuge` 5.8.0, Vite 8, Vitest 5, Playwright 1.64.1, Redocly, Ajv (existing). No new runtime dependencies.

**Spec:** master spec 10.3–10.4, 11.2–11.3 (client side), 12, 14.5; `docs/architecture/realtime-and-recovery.md`.

## Global Constraints

- Overview §4 applies. Additionally:
- React and Lit never import each other; only `@chat-platform/chat-client` and the design tokens are shared (`pnpm lint` enforces).
- Browsers never publish to Centrifugo and never see secrets; session tokens live in `localStorage` (widget) / `sessionStorage` (dashboard) under keys `cp.session.<widgetKey>` / `cp.agent.session`, every access wrapped in try/catch.
- Message bodies are rendered as text (Lit text binding / React text child), never `innerHTML`/`dangerouslySetInnerHTML`.
- Every existing `data-testid` listed in overview §5 is kept; new ones are added as listed.
- E2E tests assert persisted state through the API or `tests/support/db.ts`, never only through rendered text.
- Semantic tokens only (`--cp-*`), no hard-coded colours.

## Review Focus

1. The first `subscribed` event arrives **before** the history request returns, and a message was published in between → the message appears exactly once (`chat-client` `sync.spec.ts: eventDuringInitialLoadIsAppliedOnce`; E2E `messageDuringBootstrapIsNotLost`).
2. The user hits Send, the request times out client-side, the user hits Retry → same `clientMessageId`, one DB row, the bubble flips from `failed` to `sent` (`pending.spec.ts: retryReusesClientMessageId`; E2E `duplicateSubmissionAfterTimeoutCreatesOneRow`).
3. Centrifugo recovery fails after a long outage — the subscribed context has `wasRecovering = true && recovered = false` (Plan 01 ruling R4; a bare `recovered: false` on a first subscribe is not a failure) → the client reloads from `?after=lastSequence` and converges (`sync.spec.ts: failedRecoveryTriggersCatchUp`; E2E `centrifugoRestartConverges`).
4. A `message.created` event for a different conversation than the one open (inbox channel) must update the inbox preview/unread, not the open thread (`dashboard` unit: `inboxEventDoesNotLeakIntoOpenThread`).
5. The widget session token expired (24 h) → `POST /widget/sessions` is retried with the stale token and yields a fresh one for the same contact; history reloads; no error loop (`session.spec.ts: expiredTokenIsRefreshedOnce`).
