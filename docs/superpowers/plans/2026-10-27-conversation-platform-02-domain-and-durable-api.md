# Conversation Platform — Plan 02: Domain Model and Durable API (Phases 3–6, 8)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Read `2026-10-27-conversation-platform-00-overview.md` first (D2–D5, D7, D10–D14, D17, §5 glossary).

**Goal:** The tenant-scoped schema (`V3`), the `tenancy` module (sessions, caller resolution, local seed), the `conversation` module's durable write path (per-conversation ordering, idempotent send, lifecycle, participants, audit, history, read cursors), the `outbox` appender, and the widget/agent REST surface with its OpenAPI contract — all proven against real PostgreSQL.

**Architecture:** Spring Modulith modules `tenancy`, `conversation`, `outbox` inside `services/modulithplatformservice`. `JdbcClient` repositories with explicit SQL; one `TransactionTemplate` transaction per command; row lock on the conversation for every write; outbox rows written in the same transaction (the publisher is Plan 03). Controllers are thin; `Caller` is resolved by a `HandlerInterceptor` + argument resolver in `tenancy`.

**Tech Stack:** Spring Boot 4.1.2 (webmvc, jdbc), Spring Modulith 2.1.2, Nimbus JOSE 10.10 (session JWTs), Flyway SQL (runner image; test-scoped Flyway), Testcontainers PostgreSQL 18.6, JUnit 5, AssertJ, MockMvcTester, springdoc is **not** used (the contract is hand-written in `libs/contracts/openapi/platform-api.yaml`, validated by Redocly and `tests/contract`).

**Spec:** master spec 5, 6, 7, 8, 10.1–10.2, 14.1–14.2, 14.4; ADR-0005, 0006, 0008; `docs/architecture/{domain-model,message-lifecycle,tenant-security}.md`.

## Global Constraints

- Overview §4 applies in full. Additionally for this plan:
- Every SQL statement on a tenant-owned table includes `tenant_id = :tenant` in its predicate, or is keyed by a primary key obtained in the same transaction through a tenant-filtered statement (e.g. `updateStatus`/`bumpSequence` after `lockForUpdate(tenantId, id)`); the only cross-tenant statements are the worker claims (`OutboxRepository.claimBatch`, `ConversationRepository.claimDueAssignments`), which carry each row's `tenant_id` into every follow-up call. Any other repository method without a `tenantId` parameter is a defect.
- Transactions never call `RealtimePublisher`, `AllocationClient` or any network; outbox rows are the only side-effect channel.
- IDs are `uuidv7()` from PostgreSQL; `sequence` and `version` are assigned by SQL, never by Java arithmetic on stale reads.
- Message body: trim, 1–4000 code points, `messageType = TEXT`; `clientMessageId` 1–64 chars; reject anything else with 400 `VALIDATION_FAILED`.
- The `chat` demo module and `/api/v1/demo/*` stay untouched in this plan (removed in Plan 06); `ModularityTests` must still pass with `chat` present.
- Shared test base: `PlatformIntegrationTest` (this plan, T1) replaces the inline setup pattern of `ChatIntegrationTests`; new ITs extend it.
- Spring Modulith hides `internal/` by package, not by Java visibility: classes under `internal/` that a test in the module's root test package uses directly (`ConversationService`, `ConversationLifecycle`, `LocalSeeder`, `LocalDevGuard`, `StateEventRepository`, and in later plans `OutboxPublisher`, `AssignmentWorker`, `RetentionRepository`, …) are declared `public`, otherwise those tests do not compile (the existing code is package-private by convention).
- Run backend tests from `services/modulithplatformservice` with `JAVA_HOME="C:/Program Files/Java/jdk-25.0.3"`.

## Review Focus

1. A visitor session token for inbox A is used against a conversation of inbox B in the same tenant → 403 (`ConversationApiIT.contactCannotReadAnotherInboxConversation`).
2. Two agents of different tenants have the same agent id (`agentbob`) → each sees only its tenant's conversations (`ConversationApiIT.sameAgentIdInTwoTenantsIsIsolated`).
3. A `clientMessageId` reused with a different body after the first request timed out client-side → 409, no second row (`MessageWriteIT.reusedClientMessageIdWithDifferentBodyIs409`).
4. `before=` cursor pointing at a purged/non-existent sequence or `limit=10000` → bounded page, no error leak (`HistoryIT.pagingBeyondRangeAndOversizedLimitAreBounded`).
5. The local seeder runs twice (restart) → no duplicate tenant/inbox/contact/agent rows and the widget key is unchanged (`TenancyIT.seedIsIdempotent`).
