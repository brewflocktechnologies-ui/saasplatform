> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Read `2026-10-27-conversation-platform-00-overview.md` first (D8, D9, §1 allocation facts, §5 `assignment` types) and `docs/research/allocation-service-integration.md` (Plan 01 T2).

**Goal:** Run the existing allocation service beside the platform (own container, own PostgreSQL), talk to it through a typed HTTP gateway, drive assignment from the conversation row with a worker and a projection, expose `/assign` and agent presence, and prove the flows with an in-process allocation stub plus a gated live test against the real service.

**Architecture:** `assignment` module = `AllocationClient` (JDK `HttpClient`, 3 s timeout, headers `X-Tenant-Id`/`X-Role`/`Idempotency-Key`/`X-Correlation-Id`), `AllocationSeeder`, `AllocationLocalSeeder`. `conversation` module = `AssignmentWorker` (claims due rows with `SKIP LOCKED`, calls allocation outside transactions, projects outcomes in short transactions, emits `conversation.updated` via the outbox), `PresenceService`, `/assign`. The allocation service is unchanged apart from a Dockerfile and `.dockerignore`.

**Tech Stack:** as Plans 02–03; Docker Compose (base file gains `allocation-postgres` + `allocation-service`); allocation service image built from `D:\BYTEFLOCK\RESEARCH\Allocationservice-research\allocation-engine` with Temurin 25.

**Spec:** master spec 2.2, 11, 13, 14.3–14.4; ADR-0009; `docs/architecture/allocation-integration.md`.

## Global Constraints

- Overview §4 applies. Additionally:
- No allocation call inside a database transaction or while holding a row lock; the worker claims (commit), calls, then projects (new transaction with an `assignment_state` precondition).
- Idempotency keys: `assign:<conversationId>:<attempts>` for worker dispatches; the agent's `Idempotency-Key` header for `/assign`.
- The platform never computes capacity or availability itself; it only forwards presence and projects outcomes.
- The allocation service's own dispatch sweep stays enabled (2 s in Compose); the worker tolerates assignments it did not request.
- Allocation feature level in Compose is `operations`; `ALLOCATION_SEED_DEMO=false`; `ALLOCATION_BIND_ADDRESS=0.0.0.0` inside the container only.
- Never modify allocation-engine sources other than adding `Dockerfile`, `.dockerignore` and a README line; never commit in `D:\BYTEFLOCK`.

## Review Focus

1. The allocation service assigns a conversation through its own sweep while our worker is mid-dispatch → one projection, no `FAILED`, the agent id matches the allocation record (`AssignmentOrchestrationIT.sweepAssignmentWinsOverConcurrentDispatch`).
2. The platform restarts while rows are `REQUESTED` with a future lease → they are picked up after the lease, not lost and not dispatched twice with the same key (`AssignmentOrchestrationIT.leaseExpiryResumesWithoutDuplicateDispatch`).
3. An agent clicks "Assign to me" twice quickly with two different idempotency keys → the second gets 409 `ALLOCATION_REJECTED` (the allocation service answers a claim on an already assigned conversation with HTTP 200, outcome `REJECTED_INVALID_INPUT`, reason `CONVERSATION_NOT_ALLOCATABLE`) and the projection keeps the first assignment (`AssignmentApiIT.doubleClaimIsRejectedConsistently`).
4. The allocation service is down when the dashboard sends a heartbeat → `PUT /presence` returns 503 `ALLOCATION_UNAVAILABLE`, the dashboard keeps retrying, no exception leaks (`PresenceIT.presenceWhenAllocationDownIs503`).
5. A reopened conversation whose allocation record is still `ASSIGNED` (release never reached allocation) keeps its agent instead of failing (`AssignmentOrchestrationIT.reopenWhileAllocationStillAssignedKeepsAgent`).
