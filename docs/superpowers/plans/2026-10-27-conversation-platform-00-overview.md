## 2. Decisions (resolve the spec's open choices; every plan relies on these)

- **D1 Target and layout.** Extend `saasplatform`; no new repository. Research docs go to `docs/research/`, architecture docs to a new `docs/architecture/` directory (the existing `docs/architecture.md` file stays and links to them), ADRs follow the existing numbering in `specs/decisions/` (`ADR-0005` …), the feature spec goes to `specs/features/conversation-platform/feature.spec.md` (AGENTS.md rule 1).
- **D2 Modules** (`com.byteflock.chatplatform.*`, one Spring Modulith module per top-level package): `tenancy` (tenants, inboxes, contacts, agent roster, session tokens, caller resolution, local seed), `conversation` (conversations, participants, messages, history, read cursors, lifecycle, state events, assignment orchestration, presence/typing endpoints, channel authorization), `assignment` (typed HTTP gateway to the allocation service + seeder), `outbox` (table, appender, publisher worker, admin), `realtime` (existing; gains `broadcast`), `retention` (policies, purge, admin), plus existing `shared`, `health`, `bootstrap`. The `chat` demo module is removed in Plan 06 once the frontends use the new APIs. Allowed dependencies: `conversation → tenancy, assignment, outbox, realtime`; `outbox → realtime, tenancy`; `retention → tenancy`; `health → assignment`; `assignment → tenancy` (only for the local-dev admin tenants endpoint and seeding order); `tenancy → (none)`. Every module may additionally use `shared` (public `Problems` helper, `Clock` bean); if a `package-info.java` declares `@ApplicationModule(allowedDependencies = …)`, list `shared` there too, otherwise `ModularityTests` fails.
- **D3 Persistence.** `JdbcClient` + hand-written parameterized SQL (existing convention), READ COMMITTED with explicit row locks, Flyway SQL under `database/flywayMigration/sql/V3__conversation_platform.sql` (append-only; V2 tables stay untouched and are dropped by a later migration only after Plan 06). Every tenant-owned table carries `tenant_id` and every statement filters on it (exceptions: the id-only authorization probe and primary-key statements after a tenant-filtered lock or lookup, §8 R-P6).
- **D4 Ordering.** Strict per-conversation order: `conversations.last_sequence` incremented inside the message transaction while holding `SELECT … FOR UPDATE` on the conversation row. The history cursor is `sequence`. (ADR-0006.)
- **D5 Idempotent send.** Browser clients must send `clientMessageId` (1–64 chars). Unique index `(conversation_id, sender_type, sender_id, client_message_id)`; `request_fingerprint = sha256(trimmed body)`. Same key + same fingerprint → the original message, HTTP 200; same key + different body → 409 `CLIENT_MESSAGE_ID_REUSED`.
- **D6 Outbox.** One logical `outbox_events` row per domain event with `channels text[]`; publisher claims batches with `FOR UPDATE SKIP LOCKED` + lease, publishes with Centrifugo `POST /api/broadcast` (`idempotency_key = eventId`), exponential backoff with jitter, parks after `max-attempts` only for non-transport failures (a Centrifugo error object that is not `temporary`, or HTTP 4xx); transport failures (connection refused, timeout, 5xx, `temporary` errors) retry at up to `max-backoff` and never park (Plan 01 ruling R-P30). Delivery is **at least once**; clients dedupe by `eventId` and message `id`/`sequence`. Ephemeral typing events bypass the outbox. (ADR-0007.)
- **D7 Identity (local).** One bearer mechanism for both principals: HS256 session JWTs signed with `APP_SESSION_TOKEN_HMAC_SECRET_KEY` (claims `sub`, `tenant`, `typ` = `contact|agent`, `inbox` for contacts, `exp`; contacts also `auth_time`, the first issue time, copied on refresh: an expired contact token is refreshable for `app.sessions.contact-refresh-max-age` (30 days) after it, Plan 01 ruling R-P31 M4). Visitors get one from `POST /api/v1/widget/sessions` (public `widgetKey` → inbox → contact). Agents get one from `POST /api/v1/agent/local-login` (local-dev only). Admin endpoints need `X-Admin-Token` = `APP_LOCAL_ADMIN_TOKEN` and exist only when `app.local-dev.enabled=true`; startup fails if that flag is on while `app.environment=production`. Keep the "LOCAL POC — NOT REAL AUTHENTICATION" labelling. (ADR-0008.)
- **D8 Allocation topology.** The allocation service runs as its own container with its own PostgreSQL (`allocation-postgres`), unchanged except for an added `Dockerfile`. The platform talks to it over HTTP (`assignment.AllocationClient`) with `X-Tenant-Id` = our tenant id, `X-Role` = `operator` (admin for seeding), `Idempotency-Key` on dispatch/claim/reassign. The allocation service owns assignment records and agent availability; the platform stores a **projection** on `conversations` (`assignment_state`, `assigned_agent_id`, `assignment_decision_id`, `assignment_reason`). No cross-service transaction: the conversation row is the durable request and a scheduled `AssignmentWorker` drives it (`REQUESTED → dispatch`, `QUEUED → poll`, `RELEASE_PENDING → resolve`, `REOPEN_PENDING → requeue REOPEN`, `FAILED → re-read every failed-poll`, R-P17; see §8). Allocation ids: our tenant id, our conversation UUID string, `inboxes.allocation_queue_id`, our agent id. Required allocation feature level: `operations` (claim + reassignment). (ADR-0009.)
- **D9 Presence.** Agent availability lives in the allocation service (`POST /api/v1/agents/{id}/presence`, 60 s heartbeat TTL). The dashboard sends `PUT /api/v1/agent/presence` on change and every 30 s as a heartbeat. "Connected" is the client's socket state; "available" is the allocation status; "assigned" is the projection. The widget's `agentOnline` flag is computed server-side from allocation presence (`stale-after` 60 s) and refreshed on conversation events and a 30 s poll. No second availability store.
- **D10 Lifecycle.** Statuses `OPEN`, `PENDING`, `RESOLVED` (`SNOOZED` deferred). Archive is an independent marker (`archived_at`, `archived_by`, `archive_reason`). Repeating a command that is already satisfied is a 200 no-op (on an archived conversation only `RESOLVE` and `ARCHIVE` are; `REOPEN` of an archived `OPEN` and `MARK_PENDING` of an archived `PENDING` conversation are 409 `CONVERSATION_ARCHIVED`, Plan 01 ruling R-P31 M14); forbidden transitions are 409 `INVALID_TRANSITION`; `expectedVersion` mismatch is 409 `STALE_VERSION`; check order: an already-satisfied command is the 200 no-op even when its `expectedVersion` is stale (safe client retries), otherwise a mismatching `expectedVersion` is `STALE_VERSION` before the transition table is consulted (two agents' conflicting commands with one version → one 200, one `STALE_VERSION`). Message policy: contact message into `RESOLVED` auto-reopens (state event `REOPENED_BY_CONTACT`, allocation `REOPEN_PENDING`); agent message into `RESOLVED` is 409 `CONVERSATION_RESOLVED`; any message into an archived conversation is 409 `CONVERSATION_ARCHIVED` (the widget then starts a new conversation).
- **D11 Start/resume.** `POST /api/v1/widget/conversations` returns the contact's latest non-archived conversation in the inbox (any status) or creates one. Partial unique index `(tenant_id, inbox_id, contact_id) WHERE status <> 'RESOLVED' AND archived_at IS NULL` makes creation race-safe (`INSERT … ON CONFLICT … DO NOTHING`, then re-read, as the V2 demo does). The same index means a contact has at most one non-resolved, non-archived conversation per inbox: an `unarchive` or `reopen` (or a contact message that would auto-reopen) that would create a second one is 409 `CONVERSATION_ACTIVE_EXISTS` (translate the unique violation; nothing is written).
- **D12 Channels and events.** `chat:conversation:<uuid>` (kept) and `chat:inbox:<tenantId>:<inboxUuid>` (replaces `chat:inbox`). Envelope `{eventId, eventType, schemaVersion, tenantId, conversationId, occurredAt, data}`. Event types: `message.created`, `conversation.created`, `conversation.updated` (`data.change` ∈ ASSIGNED, RESOLVED, REOPENED, PENDING, ARCHIVED, UNARCHIVED, ASSIGNMENT_QUEUED, ASSIGNMENT_FAILED, ASSIGNMENT_UPDATED), `typing` (ephemeral). `version` increments if and only if a `conversation.created`/`conversation.updated` row is appended in the same transaction (the purge excepted); `ASSIGNMENT_UPDATED` covers every projection change that fits none of the other values: the release to `NONE` and moves into `REQUESTED`, `RELEASE_PENDING`, `REOPEN_PENDING` (Plan 01 ruling R-P23). Centrifugo `chat` namespace gets `history_size: 100`, `history_ttl: "300s"`, `force_recovery: true` as a short-gap optimisation only; the client always reconciles from the API (`?after=<lastSequence>`) on every `subscribed`.
- **D13 History and read state.** `GET …/messages?before=<seq>&limit=50` (older page) and `?after=<seq>&limit=200` (catch-up); response `{items[], hasMore}` ascending by `sequence`; max limit 200. Read cursor per `(conversation, participantType, participantId)` with `last_read_sequence`, monotonic (`GREATEST`); unread = `last_sequence − cursor`, 0 once the conversation is purged (Plan 01 ruling R-P31 M5). A cursor write locks the conversation row `FOR KEY SHARE` before the upsert, the same order as a send (R-P26).
- **D14 Participants and authorization.** Contact: only its own conversations. Agent: may read every conversation of its tenant's inboxes and may send to any non-archived one (sending adds an `AGENT` participant row); assignment routes work but does not gate sending. Cross-tenant access is 403 at the API and at subscription-token issuance.
- **D15 Attachments.** Schema only (`message_attachments`, `reply_to_message_id`) — classified NEXT. No upload endpoint, no object storage. Purge still deletes attachment rows.
- **D16 Retention/purge.** Per-tenant `retention_policies(resolved_retention_days, legal_hold)`; eligible = not purged AND ((`RESOLVED` AND `resolved_at < cutoff`) OR (archived AND `archived_at < cutoff`)), tenant not on hold, the hold re-checked before every batch (Plan 01 rulings R-P25, R-P31 M9). Purge hard-deletes messages, attachment rows, read cursors and the conversation's `outbox_events` rows (their payloads embed message bodies) in bounded batches, sets `conversations.purged_at`, sets `RESOLVED` (`resolved_at = COALESCE(resolved_at, now)`) where the conversation was not, and, when not yet archived, `archived_at` (`archived_by = 'system:retention'`) so a purged conversation is `RESOLVED` and archived and follows the archived rules (new messages are 409 and the widget starts a new conversation), clears the preview, `archive_reason` and the free-text `reason` in the conversation's state-event `details` (R-P31 M10), keeps conversation and state-event rows, writes no state event and no outbox row. Admin-only, dry-run first, `cutoff` override allowed in local-dev for verification. Not scheduled in MVP.
- **D17 Rate limits.** In-memory token buckets per principal (`ponytail:` per-instance; a shared store when there is more than one backend instance): sessions 10/min per widget key + client IP, messages 30/min per principal (bucket key `msg:<tenantId>:<principalType>:<principalId>`, Plan 01 ruling R-P31 M3), typing 1 per 2 s per principal+conversation. 429 problem details.
- **D18 Frontends.** Extend the existing Lit widget and Next.js dashboard; no framework change. `libs/chat-client` stays framework-agnostic and gains sync/pending/typing helpers. Existing `data-testid`s are kept so the current E2E style continues.
- **D19 Tests.** JUnit 5 + Testcontainers PostgreSQL (real `V1…V3` SQL), `CentrifugoStub` and a new `AllocationStub` (in-process `HttpServer`), Playwright for E2E/contract, a Node load harness built on the official `centrifuge` SDK with Node 24's global `WebSocket` (no `ws` dependency; `tests/contract` already runs the SDK in Node this way) so it speaks the real protocol. No H2.
- **D20 Commits.** Commit in `saasplatform` after each task (conventional messages). Never commit in `D:\BYTEFLOCK` root or touch the reference checkouts. The only change outside `saasplatform` is `allocation-engine/Dockerfile` (+ a README line), uncommitted like the rest of that project.

`interface TenantDirectory { Optional<Inbox> inboxByWidgetKey(String); Optional<Inbox> inbox(String tenantId, UUID); List<Inbox> inboxes(String tenantId); Optional<Agent> agent(String tenantId, String agentId); List<Agent> agents(String tenantId); Contact ensureContact(String tenantId, String externalId, String displayName); Contact createAnonymousContact(String tenantId); Optional<Contact> contact(String tenantId, UUID contactId); void ensureTenant(String tenantId, String name); Inbox ensureInbox(String tenantId, String name, String widgetKey, String allocationQueueId); Agent ensureAgent(String tenantId, String agentId, String displayName); }` (`ensure*` are idempotent upserts — `ensureInbox` by `widget_key` — used by the local seeder, `TenancyIT`/`ConversationTestData` and the admin tenants endpoint); `class SessionTokens { IssuedSession issueContact(String tenantId, UUID contactId, UUID inboxId); IssuedSession issueAgent(String tenantId, String agentId); Caller verify(String token) throws InvalidSessionException; Caller verifyForRefresh(String token) throws InvalidSessionException; }` (`verifyForRefresh` checks signature and `typ=contact` but not `exp`, and rejects a token whose `auth_time` is more than `app.sessions.contact-refresh-max-age` ago — R-P31 M4; `record LocalDevProperties(boolean enabled, String adminToken)` bound to `app.local-dev.*`.
- `conversation` [02–04]: `enum ConversationStatus { OPEN, PENDING, RESOLVED }`; `enum AssignmentState { NONE, REQUESTED, QUEUED, ASSIGNED, RELEASE_PENDING, REOPEN_PENDING, FAILED }`; `sealed interface AssignmentInfo permits AssignmentView, ContactAssignmentView { AssignmentState state(); String agentId(); }`; `record AssignmentView(AssignmentState state, String agentId, UUID decisionId, String reason, String explanation) implements AssignmentInfo` (agent callers); `record ContactAssignmentView(AssignmentState state, String agentId) implements AssignmentInfo` (contact callers and event payloads; both keys always serialised, `agentId` null when none — R-P29); `record ConversationView(UUID id, String tenantId, UUID inboxId, UUID contactId, String contactDisplayName, ConversationStatus status, long version, long lastSequence, OffsetDateTime lastMessageAt, String lastMessagePreview, AssignmentInfo assignment, OffsetDateTime resolvedAt, OffsetDateTime archivedAt, OffsetDateTime purgedAt, OffsetDateTime createdAt, OffsetDateTime updatedAt, long unreadCount, Boolean agentOnline)` (`purgedAt` nullable; `unreadCount` is 0 when `purgedAt` is set — R-P31 M5); `record MessageView(UUID id, UUID conversationId, long sequence, String senderType, String senderId, String messageType, String body, String clientMessageId, OffsetDateTime createdAt, OffsetDateTime editedAt, OffsetDateTime deletedAt)`; `record MessagePage(List<MessageView> items, boolean hasMore)`; `record SendMessageRequest(String clientMessageId, String body)`; `record CommandRequest(Long expectedVersion, String reason)`; `enum AssignMode { AUTO, CLAIM, REASSIGN }`; `record AssignRequest(AssignMode mode, Long expectedVersion)`; `final class Channels { static String conversation(UUID id); static String inbox(String tenantId, UUID inboxId); static Optional<UUID> conversationId(String channel); static Optional<InboxRef> inboxRef(String channel); }`; `record InboxRef(String tenantId, UUID inboxId)`. Visibility (R-P3, R-P29): agent callers get the full `AssignmentView` (all five keys, null when unknown); CONTACT callers and every `conversation.created`/`conversation.updated` event payload get `ContactAssignmentView` — exactly the keys `state` and `agentId`, both always present; `decisionId`, `reason`, `explanation` do not exist there (R-P29 supersedes R-P21's serialisation detail; no null-dropping serialiser). Internal, not public API (R-P6): `ConversationRepository.tenantAndInboxOf(UUID id)` is the single id-only authorization probe on a tenant-owned table, besides primary-key statements after a tenant-filtered lock or lookup (R-P6 amended); it returns only `(tenantId, inboxId, contactId)` and is used only to answer 403 (exists, other scope) versus 404 (no such id).

- **D** `view=queue` includes `FAILED` so agents can retry with `/assign`, and `REOPEN_PENDING` (a reopened or unarchived conversation waiting for its requeue; Plan 01 ruling R-P31 M2).
- **E** Purge also archives the conversation (`archived_by = 'system:retention'`), so purged conversations follow the archived rules.
- **F** `/assign` with a `QUEUED_*` outcome answers 200 with `assignment.state = QUEUED`; only rejections are 409.
- **G** Local profile session rate limit stays 600/min (the reviewer's value); E2E/load runs may override via `APP_RATE_LIMIT_*`.
- **H** `CentrifugoStub` simulates downtime with a `setDown` flag instead of rebinding the port.
- **I** Plan 06 T1 keeps the demo client under `lib/demo/` with `Demo`-prefixed exports until T4, so every commit type-checks.
- **J** Backoff jitter is applied before the cap, so delays never exceed `max-backoff`.
